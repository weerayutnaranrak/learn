Clean & Onion Architecture

Architecture ที่วาง Business Logic ไว้ตรงกลาง ไม่ขึ้นกับ Framework, Database, หรือ UI — เปลี่ยน infrastructure ได้โดยไม่ต้องแก้ business rules เลยสักบรรทัด

😣 ปัญหาที่ทั้งสองแก้ไข
ทำไมถึงต้องการ architecture แบบนี้?
ปัญหา 1

Business Logic ผูกติดกับ Framework

เปลี่ยน ORM, HTTP library, หรือ DB ไม่ได้ เพราะ logic กระจายอยู่ทั่ว codebase

ปัญหา 2

Unit Test ทำยาก

ต้องมี DB connection จริงถึงจะ test ได้ ทำให้ test ช้า brittle และ developer ไม่ test

ปัญหา 3

Architecture ไม่ "Scream"

ดู codebase แล้วไม่รู้ว่า app ทำอะไร เห็นแต่ controllers, models, views — ไม่เห็น business intent

หลักการแก้ปัญหา: ทำให้ Business Logic เป็น Pure Go ที่ไม่ import อะไรนอกจาก standard library — แล้วให้ Infrastructure implement interface ที่ Business Logic กำหนด (Dependency Inversion)

🏛️ Clean Architecture
โดย Robert C. Martin (Uncle Bob) — 2012 · เน้นแยก Enterprise Rules ออกจาก Application Rules อย่างชัดเจน
Clean Architecture — 4 Concentric Rings
🎯
Innermost
Entities
Enterprise Business Rules — struct, methods, business invariants ที่ไม่เปลี่ยนแปลงตาม use case

✓ Pure Go — ไม่ import อะไร
✓ Validate ข้อมูลในตัวเอง
✓ Business rule อยู่ที่นี่ เช่น order.Confirm()
⚙️
2nd Ring
Use Cases
Application Business Rules — orchestrate entities เพื่อให้งานสำเร็จตาม use case

✓ Input/Output DTO
✓ กำหนด Ports (interfaces) ที่ต้องการ
✓ ไม่รู้ว่า HTTP, DB, หรือ framework ใดใช้อยู่
🔌
3rd Ring
Interface Adapters
แปลง format ระหว่าง Use Cases กับ External World

✓ Controllers — แปลง HTTP request → Use Case Input
✓ Presenters — แปลง Use Case Output → JSON/HTML
✓ Gateways — implement interfaces ที่ Use Case กำหนด
🏗️
Outermost
Frameworks & Drivers
Implementation details — glue code ที่ไม่ควรมี business logic

✓ Database drivers (postgres, redis)
✓ Web frameworks (chi, gin, fiber)
✓ External services (email, SMS, S3)
Humble Object Pattern: Frameworks & Drivers เป็นแค่ "glue" — business logic ไม่ควรมีแม้แต่บรรทัดเดียวที่นี่ หากเพิ่ม logic ใน handler หรือ repo ให้ย้ายไป use case หรือ entity แทน
🧅 Onion Architecture
โดย Jeffrey Palermo — 2008 · เน้น Domain Model เป็นศูนย์กลาง มี Domain Services เป็นชั้นพิเศษ
Onion Architecture — Domain at the Core
💎
Innermost
Domain Model
Entities, Value Objects, Aggregates — แนวคิดจาก DDD ที่อยู่ที่นี่

✓ Aggregate Root ควบคุม invariants
✓ Value Object ไม่มี ID
✓ Pure Go — ไม่ import อะไร
⚗️
2nd Ring
Domain Services
Business logic ที่ต้องรู้จักหลาย Domain Objects — ไม่เหมาะอยู่ใน Model เดี่ยว

✓ ตรวจสอบ business rule ที่ span หลาย aggregate
✓ Calculation ที่ซับซ้อน
✓ ไม่มีใน Clean Architecture — ถือว่าอยู่ใน Entities
🎭
3rd Ring
Application Services
Orchestrate Domain — รับ command จากนอก แล้วเรียก domain services + repositories

✓ Transaction management
✓ กำหนด Repository interfaces
✓ เทียบเท่า Use Cases ใน Clean Architecture
🔧
Outermost
Infrastructure
Implements interfaces ที่ Application Services กำหนด

✓ Persistence (DB repositories)
✓ Web layer (HTTP handlers)
✓ Tests อยู่ชั้นนี้ด้วย — ทดสอบได้ทุก layer
Onion vs Clean — ความต่างหลัก: Onion มี Domain Services เป็น explicit layer แยกจาก Domain Model ทำให้ business logic ที่ต้องรู้จักหลาย aggregate มีที่อยู่ที่ชัดเจน — Clean Architecture รวมทุกอย่างไว้ใน Entities layer

entity/order.go — Enterprise Business Rules Go · Entity 
package entity

import "errors"

var (
	ErrOrderNotFound   = errors.New("order not found")
	ErrOrderNotPending = errors.New("order is not in pending status")
	ErrEmptyItems      = errors.New("order must have at least one item")
)

type OrderStatus string

const (
	Pending   OrderStatus = "pending"
	Confirmed OrderStatus = "confirmed"
	Cancelled OrderStatus = "cancelled"
)

type OrderItem struct {
	ProductID string
	Name      string
	Qty       int
	Price     float64
}

// Order — Enterprise Business Rule
// ไม่ depend อะไรเลย ไม่รู้จัก DB, HTTP, หรือ Framework ใดๆ
type Order struct {
	ID     string
	UserID string
	Items  []OrderItem
	Status OrderStatus
}

func NewOrder(id, userID string, items []OrderItem) (*Order, error) {
	if len(items) == 0 {
		return nil, ErrEmptyItems
	}
	return &Order{ID: id, UserID: userID, Items: items, Status: Pending}, nil
}

// Confirm — business rule: ยืนยันได้เฉพาะ order ที่ pending เท่านั้น
func (o *Order) Confirm() error {
	if o.Status != Pending {
		return ErrOrderNotPending
	}
	o.Status = Confirmed
	return nil
}

func (o *Order) Cancel() error {
	if o.Status == Cancelled {
		return errors.New("order already cancelled")
	}
	o.Status = Cancelled
	return nil
}

// Total — business calculation อยู่ใน Entity
func (o *Order) Total() float64 {
	var total float64
	for _, item := range o.Items {
		total += float64(item.Qty) * item.Price
	}
	return total
}

usecase/confirm_order.go — Application Business Rule Go · Use Case 
package usecase

import "myapp/entity"

// ConfirmOrder — Application Business Rule (Use Case)
// รู้จักแค่ Ports (interfaces) — ไม่รู้ว่าใคร implement
type ConfirmOrder struct {
	orders   OrderRepository
	notifier Notifier
}

func NewConfirmOrder(r OrderRepository, n Notifier) *ConfirmOrder {
	return &ConfirmOrder{orders: r, notifier: n}
}

// Input/Output DTOs — Use Case boundary ที่ชัดเจน
type ConfirmOrderInput struct {
	OrderID string
}

type ConfirmOrderOutput struct {
	OrderID string
	Status  string
	Total   float64
}

// Execute — orchestrate: ดึง Entity → call business rule → save → notify
func (uc *ConfirmOrder) Execute(in ConfirmOrderInput) (ConfirmOrderOutput, error) {
	order, err := uc.orders.FindByID(in.OrderID)
	if err != nil {
		return ConfirmOrderOutput{}, err
	}

	// Entity บังคับ business rule — Use Case แค่เรียก
	if err := order.Confirm(); err != nil {
		return ConfirmOrderOutput{}, err
	}

	if err := uc.orders.Save(order); err != nil {
		return ConfirmOrderOutput{}, err
	}

	// best-effort notification — ไม่ fail ถ้า notify ไม่ได้
	_ = uc.notifier.SendConfirmation(order)

	return ConfirmOrderOutput{
		OrderID: order.ID,
		Status:  string(order.Status),
		Total:   order.Total(),
	}, nil
}

adapter/handler/order_handler.go — Interface Adapter Go · Adapter 
package handler

import (
	"encoding/json"
	"net/http"

	"myapp/usecase"
)

// OrderHandler — Interface Adapter
// หน้าที่เดียว: แปลง HTTP request → Use Case Input, Use Case Output → HTTP response
// ไม่มี business logic ที่นี่
type OrderHandler struct {
	confirmOrder *usecase.ConfirmOrder
}

func NewOrderHandler(uc *usecase.ConfirmOrder) *OrderHandler {
	return &OrderHandler{confirmOrder: uc}
}

func (h *OrderHandler) ConfirmOrder(w http.ResponseWriter, r *http.Request) {
	id := r.PathValue("id") // Go 1.22+ built-in path params

	out, err := h.confirmOrder.Execute(usecase.ConfirmOrderInput{OrderID: id})
	if err != nil {
		code := http.StatusInternalServerError
		if err.Error() == "order not found" {
			code = http.StatusNotFound
		}
		http.Error(w, err.Error(), code)
		return
	}

	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(out)
}

// GetOrders handler ตัวอย่างเพิ่มเติม
func (h *OrderHandler) RegisterRoutes(mux *http.ServeMux) {
	mux.HandleFunc("PUT /orders/{id}/confirm", h.ConfirmOrder)
}
infrastructure/postgres_order_repo.go — Frameworks & Drivers Go · Infrastructure 
package infrastructure

import (
	"database/sql"

	"myapp/entity"
)

// PostgresOrderRepo implements usecase.OrderRepository
// เปลี่ยน DB ได้โดยไม่กระทบ Use Case หรือ Entity เลย
type PostgresOrderRepo struct {
	db *sql.DB
}

func NewPostgresOrderRepo(db *sql.DB) *PostgresOrderRepo {
	return &PostgresOrderRepo{db: db}
}

func (r *PostgresOrderRepo) FindByID(id string) (*entity.Order, error) {
	row := r.db.QueryRow(
		`SELECT id, user_id, status FROM orders WHERE id = $1`, id,
	)
	o := &entity.Order{}
	if err := row.Scan(&o.ID, &o.UserID, &o.Status); err != nil {
		if err == sql.ErrNoRows {
			return nil, entity.ErrOrderNotFound
		}
		return nil, err
	}
	// load items from order_items table ...
	return o, nil
}

func (r *PostgresOrderRepo) Save(order *entity.Order) error {
	_, err := r.db.Exec(
		`UPDATE orders SET status = $1, updated_at = NOW() WHERE id = $2`,
		string(order.Status), order.ID,
	)
	return err
}

func (r *PostgresOrderRepo) FindByUserID(userID string) ([]*entity.Order, error) {
	rows, err := r.db.Query(
		`SELECT id, user_id, status FROM orders WHERE user_id = $1`, userID,
	)
	if err != nil {
		return nil, err
	}
	defer rows.Close()
	var orders []*entity.Order
	for rows.Next() {
		o := &entity.Order{}
		rows.Scan(&o.ID, &o.UserID, &o.Status)
		orders = append(orders, o)
	}
	return orders, nil
}
cmd/main.go — Dependency Injection Wiring Go · Composition Root 
package main

import (
	"database/sql"
	"log"
	"net/http"

	_ "github.com/lib/pq"

	"myapp/adapter/handler"
	"myapp/infrastructure"
	"myapp/usecase"
)

func main() {
	// 1. Infrastructure (outermost) — concrete implementations
	db, err := sql.Open("postgres", "postgres://user:pass@localhost/mydb")
	if err != nil {
		log.Fatal(err)
	}
	defer db.Close()

	// 2. Wire dependencies — Outer depends on Inner, never reverse
	orderRepo := infrastructure.NewPostgresOrderRepo(db)    // implements usecase.OrderRepository
	notifier  := infrastructure.NewEmailNotifier()          // implements usecase.Notifier

	// 3. Use Cases — depend only on interfaces (Ports)
	confirmOrder := usecase.NewConfirmOrder(orderRepo, notifier)

	// 4. Adapters — depend on Use Cases
	orderHandler := handler.NewOrderHandler(confirmOrder)

	// 5. Framework wiring (outermost)
	mux := http.NewServeMux()
	orderHandler.RegisterRoutes(mux)

	log.Println("Starting server on :8080")
	log.Fatal(http.ListenAndServe(":8080", mux))
}

domain/model/order.go — Domain Model (Aggregate Root) Go · Domain Model 
package model

import "errors"

// Money — Value Object (immutable, ไม่มี ID)
type Money struct {
	Amount   float64
	Currency string
}

func (m Money) Add(other Money) (Money, error) {
	if m.Currency != other.Currency {
		return Money{}, errors.New("currency mismatch")
	}
	return Money{Amount: m.Amount + other.Amount, Currency: m.Currency}, nil
}

// OrderItem — Value Object
type OrderItem struct {
	ProductID string
	Name      string
	Qty       int
	UnitPrice Money
}

func (i OrderItem) Subtotal() Money {
	return Money{Amount: float64(i.Qty) * i.UnitPrice.Amount, Currency: i.UnitPrice.Currency}
}

type OrderStatus string

const (
	OrderPending   OrderStatus = "pending"
	OrderConfirmed OrderStatus = "confirmed"
	OrderCancelled OrderStatus = "cancelled"
)

// Order — Aggregate Root
// ควบคุม invariants ของ aggregate ทั้งหมด
type Order struct {
	ID     string
	UserID string
	Items  []OrderItem
	Status OrderStatus
}

func NewOrder(id, userID string, items []OrderItem) (*Order, error) {
	if len(items) == 0 {
		return nil, errors.New("order must have at least one item")
	}
	return &Order{ID: id, UserID: userID, Items: items, Status: OrderPending}, nil
}

func (o *Order) Confirm() error {
	if o.Status != OrderPending {
		return errors.New("can only confirm a pending order")
	}
	o.Status = OrderConfirmed
	return nil
}

// Total — calculation อยู่ใน Aggregate Root
func (o *Order) Total() Money {
	var total float64
	for _, item := range o.Items {
		total += item.Subtotal().Amount
	}
	return Money{Amount: total, Currency: "THB"}
}

domain/service/order_domain_service.go — Domain Service Go · Domain Service 
package domainservice

import (
	"errors"

	"myapp/domain/model"
)

// OrderDomainService — logic ที่ต้องรู้จักหลาย Domain Objects
// ไม่เหมาะอยู่ใน Order.Confirm() เพราะต้องรู้จัก User ด้วย
type OrderDomainService struct{}

// CanPlaceOrder — business rule ที่ span หลาย aggregate (Order + User)
// ถ้าใส่ใน Order.go → Order ต้อง depend on User → ผิด boundary
func (s *OrderDomainService) CanPlaceOrder(user *model.User, items []model.OrderItem) error {
	if user.IsBanned {
		return errors.New("banned users cannot place orders")
	}
	if !user.IsEmailVerified {
		return errors.New("please verify email before ordering")
	}

	total := s.calculateTotal(items)
	if total > user.CreditLimit {
		return errors.New("order total exceeds credit limit")
	}
	return nil
}

func (s *OrderDomainService) calculateTotal(items []model.OrderItem) float64 {
	var total float64
	for _, item := range items {
		total += item.Subtotal().Amount
	}
	return total
}

// ApplyBulkDiscount — pricing rule ที่ซับซ้อน ไม่เหมาะอยู่ใน model
func (s *OrderDomainService) ApplyBulkDiscount(order *model.Order) float64 {
	total := order.Total().Amount
	switch {
	case total >= 10000:
		return total * 0.15 // 15% discount
	case total >= 5000:
		return total * 0.10
	default:
		return 0
	}
}
application/order_app_service.go — Application Service Go · Application Service 
package application

import (
	"github.com/google/uuid"

	"myapp/domain/model"
	"myapp/domain/port"
	domainservice "myapp/domain/service"
)

// OrderAppService — orchestrate domain objects
// ไม่มี business logic เอง แค่ประสาน Domain Services + Repositories
type OrderAppService struct {
	orders      port.OrderRepository
	users       port.UserRepository
	notifier    port.Notifier
	orderDomain *domainservice.OrderDomainService
}

func NewOrderAppService(
	orders port.OrderRepository,
	users port.UserRepository,
	notifier port.Notifier,
) *OrderAppService {
	return &OrderAppService{
		orders:      orders,
		users:       users,
		notifier:    notifier,
		orderDomain: &domainservice.OrderDomainService{},
	}
}

type PlaceOrderCmd struct {
	UserID string
	Items  []model.OrderItem
}

func (s *OrderAppService) PlaceOrder(cmd PlaceOrderCmd) (*model.Order, error) {
	// 1. Load domain objects
	user, err := s.users.FindByID(cmd.UserID)
	if err != nil {
		return nil, err
	}

	// 2. Domain Service ตรวจสอบ business rule (ต้องรู้จัก User + Items)
	if err := s.orderDomain.CanPlaceOrder(user, cmd.Items); err != nil {
		return nil, err
	}

	// 3. Domain Model สร้าง Aggregate
	order, err := model.NewOrder(uuid.NewString(), cmd.UserID, cmd.Items)
	if err != nil {
		return nil, err
	}

	// 4. Persist
	if err := s.orders.Save(order); err != nil {
		return nil, err
	}

	// 5. Side effects (notification)
	_ = s.notifier.Notify(user.Email, "Your order has been placed!")

	return order, nil
}

func (s *OrderAppService) ConfirmOrder(orderID string) error {
	order, err := s.orders.FindByID(orderID)
	if err != nil {
		return err
	}
	if err := order.Confirm(); err != nil { // Domain Model business rule
		return err
	}
	return s.orders.Save(order)
}

package persistence

import (
	"database/sql"

	"myapp/domain/model"
)

// PostgresOrderRepo implements domain/port.OrderRepository
// Infrastructure อยู่ชั้นนอกสุด — depend on domain, ไม่ใช่ domain depend on infrastructure
type PostgresOrderRepo struct{ db *sql.DB }

func NewPostgresOrderRepo(db *sql.DB) *PostgresOrderRepo {
	return &PostgresOrderRepo{db: db}
}

func (r *PostgresOrderRepo) FindByID(id string) (*model.Order, error) {
	row := r.db.QueryRow(`SELECT id, user_id, status FROM orders WHERE id=$1`, id)
	o := &model.Order{}
	if err := row.Scan(&o.ID, &o.UserID, &o.Status); err != nil {
		return nil, err
	}
	return o, nil
}

func (r *PostgresOrderRepo) Save(order *model.Order) error {
	_, err := r.db.Exec(
		`INSERT INTO orders(id,user_id,status) VALUES($1,$2,$3)
		 ON CONFLICT(id) DO UPDATE SET status=$3`,
		order.ID, order.UserID, string(order.Status),
	)
	return err
}

// infrastructure/web/order_handler.go
package web

import (
	"encoding/json"
	"net/http"

	"myapp/application"
	"myapp/domain/model"
)

type OrderHandler struct {
	svc *application.OrderAppService
}

func NewOrderHandler(svc *application.OrderAppService) *OrderHandler {
	return &OrderHandler{svc: svc}
}

func (h *OrderHandler) PlaceOrder(w http.ResponseWriter, r *http.Request) {
	var cmd application.PlaceOrderCmd
	if err := json.NewDecoder(r.Body).Decode(&cmd); err != nil {
		http.Error(w, "invalid body", http.StatusBadRequest)
		return
	}
	order, err := h.svc.PlaceOrder(cmd)
	if err != nil {
		http.Error(w, err.Error(), http.StatusUnprocessableEntity)
		return
	}
	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(http.StatusCreated)
	json.NewEncoder(w).Encode(order)
}

ทั้งสอง architecture มี trade-off ที่ต้องพิจารณา
✅ ใช้ Clean Architecture เมื่อ
• ต้องการ Use Cases ที่ชัดเจน เป็น entry point
• Team ไม่คุ้นกับ DDD concepts
• App ขนาดกลาง-ใหญ่ที่ต้องการ testability สูง
• ต้องการ Input/Output DTOs ที่เข้มงวด
• อยากแยก business rules หลายชั้น ไม่รวมกันใน model
✅ ใช้ Onion Architecture เมื่อ
• Domain ซับซ้อน มี multiple aggregates
• Team คุ้นกับ DDD (Entities, VOs, Aggregates)
• มี business logic ที่ span หลาย domain objects
• ต้องการ Domain Services layer ที่แยกออกมาชัดเจน
• E-commerce, ERP, Banking systems
⚠️ ไม่เหมาะเมื่อ
• CRUD App ง่ายๆ — overkill มาก
• Team เล็ก deadline ตึง — boilerplate เยอะ
• Microservice ที่ทำงานเดียวเฉพาะเจาะจง
• Prototype หรือ MVP ที่ requirements เปลี่ยนเร็ว
💡 Tips จากประสบการณ์จริง
• เริ่มจาก Hexagonal ถ้าทีมยังใหม่กับ concept
• ในทางปฏิบัติ Clean + Onion มักผสมกัน
• ไม่ต้องทำตามกฎ 100% — เอาหลักการไปใช้
• Rule of Thumb: ถ้า test ยาก → แยก layer
