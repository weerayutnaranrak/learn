λ Why Functional Programming?ทำไมต้อง Functional Programming?

Functional Programming (FP) is a style of writing code that treats computation as the evaluation of mathematical functions — avoiding mutable state and side effects. The goal: code that is concise, predictable, and trustworthy. Functional Programming (FP) คือแนวคิดการเขียนโปรแกรมที่มองการประมวลผลเป็นการประเมินค่าฟังก์ชันทางคณิตศาสตร์ — หลีกเลี่ยง mutable state และ side effects เป้าหมาย: โค้ดที่ กระชับ, คาดเดาได้, และน่าเชื่อถือ

💡
"A function that does one thing is a function you can trust. When you can trust every small piece of your system, you can build complex architecture without fear of it collapsing like a house of cards." "ฟังก์ชันที่ทำสิ่งเดียวคือฟังก์ชันที่คุณไว้วางใจได้ เมื่อคุณไว้ใจชิ้นส่วนเล็กๆ ทุกชิ้นในระบบ คุณจะสร้าง architecture ที่ซับซ้อนได้โดยไม่กลัวว่ามันจะพังเหมือนบ้านไพ่"
The Holy Grail of Softwareเป้าหมายสูงสุดของซอฟต์แวร์
✂️
Conciseกระชับ (Concise)
Shorter code, fewer abstractions, less to read and maintain.โค้ดสั้นลง, ลด abstraction ที่ไม่จำเป็น, อ่านและ maintain ง่ายขึ้น
🏆
Trustworthyน่าเชื่อถือ (Trustworthy)
Reliable and predictable — the same input always returns the same output, errors are visible, not hidden.เชื่อถือได้และคาดเดาได้ — input เดิมได้ output เดิมเสมอ, error มองเห็นได้ ไม่ซ่อน

🔍 Code Review: The Imperative TrapCode Review: กับดักของ Imperative Code

Before climbing the FP ladder, let's see what problems arise in a typical Level 0 imperative program — an RSS feed processor written without FP principles. ก่อนจะปีน FP Ladder มาดูกันก่อนว่า โปรแกรม imperative ระดับ 0 มีปัญหาอะไรบ้าง — ดูจาก RSS feed processor ที่เขียนโดยไม่ใช้หลัก FP

5 Problems Found in Imperative RSS Processorปัญหา 5 ข้อที่พบในโค้ด Imperative
🧩
1. Logic & Readability
Manual index loops (var i, while) are prone to off-by-one errors. FP prefers .map / .foreach to eliminate manual state. ลูปด้วย index มือ (var i, while) เสี่ยง off-by-one error FP ใช้ .map / .foreach แทนเพื่อลบ state มือออกไป
🔒
2. Safety & Resource Integrity
Blocking I/O freezes the thread. Manual try-finally for resource cleanup becomes a "Pyramid of Doom" when managing multiple resources. Blocking I/O หยุด thread ทั้งหมด การปิด resource ด้วย try-finally มือกลายเป็น "ปิรามิดแห่งหายนะ" เมื่อมีหลาย resource
💥
3. Resilience (The "Cruel World" Test)
Zero fault tolerance — no timeout means the program hangs forever. No retry means a temporary WiFi blip ends the job. รับ fault ไม่ได้เลย — ไม่มี timeout โปรแกรมค้างตลอดกาล, ไม่มี retry แค่ WiFi กระพริบก็จบ
📈
4. Scalability & Performance
Sequential bottleneck — 10 feeds × 2 sec = 20 sec. mkString loads the entire XML into memory, risking OutOfMemoryError. ทำทีละอัน — 10 feeds × 2 วิ = 20 วิ. mkString โหลด XML ทั้งหมดในหน่วยความจำ เสี่ยง OutOfMemoryError
🧪
5. Testing & Maintainability
Hard-wired side effects — logic is glued to real network and disk. Unit testing is impossible without integration test setup. Side effects ฝังอยู่ใน logic — ทดสอบต้องใช้ network จริงและ disk จริง ทำ unit test โดยลำพังไม่ได้
🎯
The Core Issueปัญหาที่รากเหง้า
"Telling the computer how to move memory instead of showing your intention." The fix: separate Pure Logic, Impure Effects, and Orchestration. "บอกคอมพิวเตอร์ว่า ต้องย้าย memory อย่างไร แทนที่จะแสดง ความตั้งใจ" แก้: แยก Pure Logic, Impure Effects, และ Orchestration ออกจากกัน
The Three Pillars of Any Program: Pure Logic (Math: XML → String) · Impure Effects (Actions: Fetch, Save) · Orchestration (The Story: Do this, then that) สามเสาหลักของทุกโปรแกรม: Pure Logic (คณิตศาสตร์: XML → String) · Impure Effects (การกระทำ: Fetch, Save) · Orchestration (เรื่องราว: ทำอันนี้ แล้วค่อยทำอันนั้น)

🏛️ 4 Pillars of Trustworthy Code4 เสาหลักของโค้ดที่น่าเชื่อถือ

Whether you use Scala, Kotlin, or Java, trustworthy code boils down to these four pillars: ไม่ว่าจะใช้ Scala, Kotlin, หรือ Java โค้ดที่น่าเชื่อถือสรุปได้ด้วยสี่เสาหลักนี้:

🎯
1. Determinism (Pure Functions)
Same input → same output, always. No hidden globals, no DB writes inside logic functions. Input เดิม → output เดิม เสมอ ไม่มี global แอบซ่อน ไม่มีเขียน DB อยู่ใน logic function
  • No setup/teardown needed for testsไม่ต้อง setup/teardown ใน test
  • Logic in isolation, verifiable foreverทดสอบ logic แยกส่วนได้ตลอด
🏷️
2. Strong, Expressive Typing
Use Email type instead of String. Make illegal states unrepresentable at compile time. ใช้ type Email แทน String ทั่วไป ทำให้ state ที่ผิดกฎ compile ไม่ผ่าน
  • No 50× null checks everywhereไม่ต้อง check null 50 จุดทั่วโค้ด
  • Compiler = first line of defenseCompiler คือด่านแรกของการป้องกัน
📝
3. Declarative Logic (What, not How)
Focus on intent, not manual steps. Replace loops and nested if-else with map, filter, retry. มุ่งที่ intent ไม่ใช่ขั้นตอนมือ แทน loop และ if-else ซ้อนกันด้วย map, filter, retry
  • Standard operators = already battle-testedOperator มาตรฐาน = ผ่านการทดสอบมาแล้ว
  • Less room for off-by-one mistakesโอกาส off-by-one น้อยลงมาก
🛡️
4. Total Error Handling
Treat errors as values, not explosions. Return Either[Error, Result] instead of throwing exceptions. มองว่า error คือ ค่า ไม่ใช่ระเบิด คืน Either[Error, Result] แทนการ throw exception
  • Errors visible in the function signatureError มองเห็นได้จาก signature ของฟังก์ชัน
  • Unified pipeline, no scattered try-catchจัดการใน pipeline เดียว ไม่กระจาย try-catch

🪜 The 7 Levels of Functional Programmingบันได 7 ขั้นของ Functional Programming

Popularized by John A. De Goes (creator of ZIO), this hierarchy maps a programmer's journey from imperative "how" thinking to declarative "what" thinking. Each level builds on the previous. ถูกทำให้แพร่หลายโดย John A. De Goes (ผู้สร้าง ZIO) ลำดับชั้นนี้แสดงการเดินทางจากความคิด "how" แบบ imperative สู่ความคิด "what" แบบ declarative แต่ละ level ต่อยอดจาก level ก่อนหน้า

  • Functions & Immutability Use val over var. Pure functions. No side effects.ใช้ val แทน var ฟังก์ชัน pure ไม่มี side effect
  • Higher-Order Functions Treat functions as data: map, filter, fold, flatMap.มองฟังก์ชันเป็นข้อมูล: map, filter, fold, flatMap
  • Algebraic Data Types (ADTs) Model data with sealed trait and case class — Sum types and Product types.สร้าง model ข้อมูลด้วย sealed trait และ case class — Sum types และ Product types
  • Error Handling & Functional Effects Option, Either, IO — manage failure and side effects as values.Option, Either, IO — จัดการ failure และ side effect ในรูปแบบ value
  • Abstracting over Execution (Typeclasses) Polymorphism via Show, Eq, Functor — where Category Theory begins.Polymorphism ผ่าน Show, Eq, Functor — จุดที่ Category Theory เริ่มปรากฏ
  • Compositional Design Monoids, Applicatives, Monads — compose complex systems from simple parts.Monoids, Applicatives, Monads — ประกอบระบบซับซ้อนจากชิ้นส่วนเล็กๆ
  • High-Level Abstractions Tagless Final, Free Monads, Recursion Schemes — zero assumptions about implementation.Tagless Final, Free Monads, Recursion Schemes — ไม่มีข้อสมมติใดๆ เกี่ยวกับ implementation
🎓
Why define these levels? To address the "intimidation factor" of FP. A developer can master Level 3 (Data Modeling) without feeling like they failed because they don't yet understand Level 7 (Category Theory abstractions). Libraries like Cats and ZIO are categorized by which level they primarily target. ทำไมต้องแบ่งระดับ? เพื่อลด "ปัจจัยน่าหวาดหวั่น" ของ FP นักพัฒนา master Level 3 (Data Modeling) ได้โดยไม่ต้องรู้สึกว่าตัวเองล้มเหลวเพราะยังไม่เข้าใจ Level 7 library อย่าง Cats และ ZIO ถูกจัดหมวดหมู่ตาม level ที่มุ่งเน้น

L1 Functions & Immutabilityฟังก์ชันและความไม่เปลี่ยนแปลง

Goal: Shift from mutable state to immutable data. A pure function has no side effects and returns the same output for the same input — always. เป้าหมาย: เปลี่ยนจาก mutable state เป็น immutable data ฟังก์ชัน pure ไม่มี side effect และคืนค่าเดิมสำหรับ input เดิมเสมอ

🔒
Immutabilityความไม่เปลี่ยนแปลง
val instead of var. Once assigned, never changed. Eliminates race conditions.val แทน var กำหนดครั้งเดียว ไม่เปลี่ยนอีก ไม่มี race condition
🎯
Pure Functionsฟังก์ชัน Pure
No globals, no I/O, no DB inside. Just logic. Testable in isolation with simple assert.ไม่มี global, I/O, DB ข้างใน แค่ logic ทดสอบแยกได้ด้วย assert เดียว
🚫
No Side Effectsไม่มี Side Effect
No hidden state changes or outputs beyond the return value. What you see = what you get.ไม่มีการเปลี่ยนแปลง state แอบซ่อน สิ่งที่เห็น = สิ่งที่ได้
level1.scala
// ❌ Imperative (Level 0) — mutable state
var count = 0
count += 1
var items = new ListBuffer[(String, String)]
var i = 0
while i < itemNodes.size do
  val item = itemNodes(i)
  items.append((item.title, item.link))
  i += 1

// ✅ Level 1 — immutable + pure function
val count    = 0
val newCount = count + 1

// Pure function: XML → List[(String,String)]
// Same XML in → same List out. Always.
def extractItems(xml: Elem): List[(String, String)] =
  (xml \\ "item").map { item =>
    val title = (item \ "title").text.trim
    val link  = (item \ "link").text.trim
    (title, link)
  }.toList
✅
Why it matters: Eliminates race conditions. Makes code easier to test and reason about. If the math works once, it works forever. ทำไมสำคัญ: ไม่มี race condition อ่านและทดสอบง่ายขึ้น ถ้า logic ถูกครั้งหนึ่ง มันจะถูกตลอดไป

L2 Higher-Order Functionsฟังก์ชันอันดับสูง

Goal: Treat functions as data — pass them as arguments, return them from functions. Stop telling the computer how to loop; tell it what transformation to apply. เป้าหมาย: มองฟังก์ชันเป็นข้อมูล — ส่งเป็น argument คืนจากฟังก์ชัน หยุดบอกคอมพิวเตอร์ว่า วนลูปอย่างไร บอกแทนว่า ต้อง transform อะไร

higher-order.scala
val numbers = List(1, 2, 3)

// map:    transform every element
val squared     = numbers.map(_ * _)          // List(1, 4, 9)

// filter: keep only elements matching predicate
val evens       = numbers.filter(_ % 2 == 0)  // List(2)

// fold:   reduce to a single value
val total       = numbers.fold(0)(_ + _)       // 6

// flatMap: transform + flatten (monadic chaining)
val pairs       = numbers.flatMap(n => List(n, n * 10))
// List(1, 10, 2, 20, 3, 30)

// pipeline: compose multiple transforms
val evenSquares = numbers
  .filter(_ % 2 == 0)
  .map(_ * _)

Currying — Function FactoryCurrying — โรงงานฟังก์ชัน

A curried function takes one argument and returns a new function waiting for the next. This lets you pre-configure logic and create specialized versions of a general function. ฟังก์ชัน curried รับ argument ทีละหนึ่งตัว และคืน ฟังก์ชันใหม่ ที่รอ argument ถัดไป ทำให้ตั้งค่า logic ล่วงหน้าและสร้างฟังก์ชันเฉพาะทางจากฟังก์ชันทั่วไปได้

currying.scala
// Standard (uncurried): (A, B) => C
def add(x: Int, y: Int): Int = x + y

// Curried: A => (B => C)
val addCurried: Int => (Int => Int) =
  x => (y => x + y)

val addFive = addCurried(5)   // returns a new function
val result  = addFive(10)     // 15

// Scala sugar — multiple parameter lists:
def log(level: String)(message: String): Unit =
  println(s"[$level] $message")

// Partially apply to create specialized loggers:
val infoLog  = log("INFO")
val errorLog = log("ERROR")

infoLog("System started")   // [INFO] System started
errorLog("Kernel panic!")   // [ERROR] Kernel panic!
🏭
Assembly Line Mental Model: Non-curried = put frame AND engine on the belt together, get the car. Curried = put the frame on, get back a new machine specifically configured to fit only that frame's engine. Mental Model โรงงาน: Non-curried = วางโครงรถและเครื่องยนต์พร้อมกัน ได้รถออกมา Curried = วางแค่โครงรถ ได้ เครื่องจักรใหม่ ที่ออกแบบมาเพื่อใส่เครื่องยนต์ของโครงนั้นโดยเฉพาะ

Extension Methods (Scala 3)Extension Methods (Scala 3)

Add new methods to existing types without modifying their source code or using inheritance. How we create fluent, concise syntax like .retryN(3) or .logTime. เพิ่ม method ใหม่ให้ type ที่มีอยู่โดยไม่ต้องแก้ source หรือใช้ inheritance วิธีสร้าง syntax ที่ลื่นไหล เช่น .retryN(3) หรือ .logTime

extension-methods.scala
extension (s: String)
  def shout: String   = s.toUpperCase + "!!!"
  def isEmail: Boolean = s.contains("@")

"hello".shout        // "HELLO!!!"
"me@home.com".isEmail // true

// Custom HOF extensions on List
extension [A](list: List[A])
  def transform[B](f: A => B): List[B] =
    if list.isEmpty then Nil
    else f(list.head) :: list.tail.transform(f)

  def keepOnly(p: A => Boolean): List[A] =
    if list.isEmpty then Nil
    else if p(list.head) then list.head :: list.tail.keepOnly(p)
    else list.tail.keepOnly(p)

// Usage — pipeline style:
val students = List("Alice", "Bob", "Charlie")
val titled   = students.transform(s => s"Title: $s")
// List("Title: Alice", "Title: Bob", "Title: Charlie")

val scores = List(100, 90, 80, 70, 60)
val high   = scores.keepOnly(_ >= 80)
// List(100, 90, 80)

L3 Algebraic Data Typesชนิดข้อมูลเชิงพีชคณิต

Goal: Stop using primitive types (String for status, -1 for missing data). Define structures that only allow valid states — "make illegal states unrepresentable." เป้าหมาย: หยุดใช้ primitive type (String สำหรับ status, -1 สำหรับข้อมูลหาย) กำหนด structure ที่ อนุญาตเฉพาะ state ที่ถูกต้อง — "ทำให้ state ที่ผิดกฎ represent ไม่ได้"

✖️
Product Types — AND
Combine multiple fields. A User is a Name AND an Age. In Scala: case class. รวมหลาย field เข้าด้วยกัน User คือ Name และ Age ใน Scala: case class
product.scala
case class Ingredient(
  name: String,
  quantity: Int
)
// n × m possible combinations
➕
Sum Types — OR
Choose between variants. A payment is CreditCard OR PayPal OR Cash — never all three. In Scala 3: enum. เลือกระหว่าง variant การชำระเงินคือ CreditCard หรือ PayPal หรือ Cash — ไม่ใช่ทั้งสาม ใน Scala 3: enum
sum.scala
enum PaymentMethod:
  case CreditCard(number: String,
                  expiration: String)
  case PayPal(email: String)
  case Cash
// n + m + p possible states

Pattern Matching — Total Exhaustive SwitchPattern Matching — Switch ที่ครอบคลุมทุกกรณี

pattern-matching.scala
def processPayment(method: PaymentMethod): String =
  method match
    case PaymentMethod.CreditCard(n, _) =>
      s"Charging card ending in ${n.takeRight(4)}"
    case PaymentMethod.PayPal(e) =>
      s"Redirecting to PayPal for $e"
    case PaymentMethod.Cash =>
      "Please pay at the counter"
// No 'default' / 'else' needed!
// Compiler knows we covered every case.

Exercise: Smart Vending Machineแบบฝึกหัด: ตู้ขายสินค้าอัจฉริยะ

vending-machine.scala
// Step 1: Product Type (case class = AND)
case class Product(name: String, price: Double, category: Category)

// Step 2: Category Sum Type (enum = OR)
enum Category:
  case Drink, Snack, FreshFood

// Step 3: Machine State — complex ADT
enum MachineState:
  case Idle
  case Selecting(item: Product)
  case Processing(item: Product, inserted: Double)
  case Dispensing(item: Product)

// Step 4: Pattern matching on state
def displayMessage(state: MachineState): String = state match
  case MachineState.Idle =>
    "Welcome! Please select an item."
  case MachineState.Selecting(p) =>
    s"Selected ${p.name}. Please insert ${p.price} THB."
  case MachineState.Processing(p, inserted) =>
    if inserted < p.price then
      s"Insufficient funds: ${p.price - inserted} remaining."
    else "Payment verified. Preparing your item..."
  case MachineState.Dispensing(p) =>
    s"Enjoy your ${p.name}!"
🚫
No Nullsไม่มี Null
In Idle state there is no item variable to even access. Compiler prevents the mistake.เมื่อ state เป็น Idle ไม่มีตัวแปร item ให้เข้าถึงเลย Compiler ป้องกันความผิดพลาด
🔍
Exhaustivityครอบคลุมทุก case
Add OutOfOrder state? Compiler warns every match that is now incomplete.เพิ่ม state OutOfOrder? Compiler เตือน ทุก match ที่ยังไม่ครอบคลุม
🔐
Data Integrityความสมบูรณ์ของข้อมูล
Cannot be in Processing without both Product and Amount. Structure enforces business rules.เป็น Processing โดยไม่มีทั้ง Product และ Amount ไม่ได้ โครงสร้างบังคับ business rules

L4 IO Monad & Functional EffectsIO Monad และ Functional Effects

Goal: Move from eager execution to lazy description. Instead of doing an action, return a Blueprint (IO) that describes what to do. Execute only at the very edge of the program. เป้าหมาย: เปลี่ยนจาก การทำทันที เป็น การอธิบายแบบ lazy แทนที่จะ ทำ action คืน Blueprint (IO) ที่อธิบายว่าจะทำอะไร Execute เฉพาะที่ขอบโปรแกรม

🎬
Analogy: Level 1–3 is a live performance — if you mess up, the show is ruined. Level 4 is a movie script. You can read it, edit it, copy it, or decide not to film it at all. // Compose blueprints safely:
def readUser(id: String): IO[Either[String, User]] =
  IO.pure(getUser(id))

def saveUser(user: User): IO[Either[String, Unit]] =
  IO.pure(Right(()))

// Chain effects — still just a blueprint:
val program: IO[Either[String, Unit]] =
  readUser("1").flatMap {
    case Left(err)   => IO.pure(Left(err))
    case Right(user) => saveUser(user)
  }

// Only here does the program ACTUALLY run:
object Main extends IOApp:
  def run(args: List[String]): IO[ExitCode] =
    program.as(ExitCode.Success)

L5 Type ClassesType Classes

A Type Class is a pattern for ad-hoc polymorphism — adding new behavior to existing types without modifying them and without inheritance. Define a "concept" (Summarizable) and provide implementations for different types separately. Type Class คือ pattern สำหรับ ad-hoc polymorphism — เพิ่ม behavior ใหม่ให้ type ที่มีอยู่โดยไม่ต้องแก้ไขและไม่ใช้ inheritance กำหนด "concept" (Summarizable) และแยก implementation ออกสำหรับแต่ละ type

The 3 Components3 องค์ประกอบ

type-class.scala
// 1. The Type Class (the interface — defines the concept)
trait Summarizable[A]:
  def summarize(value: A): String

// 2. Type Class Instances (the implementations — Scala 3 `given`)
given Summarizable[Int] with
  def summarize(value: Int): String = s"The number is $value"

given Summarizable[String] with
  def summarize(value: String): String = s"The text says: '$value'"

// 3. The Interface Surface (the usage — `using` keyword)
def printSummary[A](item: A)(using s: Summarizable[A]): Unit =
  println(s.summarize(item))

printSummary(42)           // The number is 42
printSummary("Hello Type") // The text says: 'Hello Type'

// Context Bound shorthand (same as above, just syntactic sugar):
def printSummary2[A : Summarizable](item: A): Unit =
  val s = summon[Summarizable[A]]
  println(s.summarize(item))
