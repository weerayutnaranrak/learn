🔄 What is a Finite State Machine?Finite State Machine คืออะไร?

A Finite State Machine (FSM), also called a Deterministic Finite Automaton (DFA), is a mathematical model of computation with a fixed number of states, where the current state plus an input event deterministically produces a new state. Finite State Machine (FSM) หรือ Deterministic Finite Automaton (DFA) คือแบบจำลองทางคณิตศาสตร์ที่มีจำนวน state คงที่ โดย state ปัจจุบัน + event จะกำหนด state ถัดไปอย่างแน่นอน

Formal Definitionนิยามอย่างเป็นทางการ
📦
Q — States
A finite set of states. Every possible "situation" the system can be in. e.g. {Pending, Confirmed, Shipped, Delivered, Cancelled} เซตของ state ทั้งหมดที่เป็นไปได้ เช่น {Pending, Confirmed, Shipped, Delivered, Cancelled}
⚡
Σ — Alphabet (Events)
The finite set of valid input events/actions. e.g. {confirm, ship, deliver, cancel} — events that trigger transitions เซตของ event/action ที่ valid ทั้งหมด เช่น {confirm, ship, deliver, cancel}
δ
δ — Transition Function
δ: Q × Σ → Q. Given the current state and an event, returns the next state. This is the heart of the machine. δ: Q × Σ → Q รับ state ปัจจุบัน + event แล้วคืน state ถัดไป นี่คือหัวใจของ FSM
🚀
q₀ — Start State
The initial state the machine begins in. e.g. every Order starts as Pending. state เริ่มต้น ทุก Order เริ่มที่ Pending ทุก TCP connection เริ่มที่ Closed
🏁
F — Accept States
Terminal/final states. e.g. Delivered and Cancelled are final — no further transitions are valid from these states. State สุดท้าย เช่น Delivered และ Cancelled ไม่มี transition ออกจาก state เหล่านี้
🔑
Key Property: Deterministic
For every (state, event) pair there is exactly one next state — no ambiguity, no randomness. This is the "D" in DFA. ทุกคู่ (state, event) มี next state แค่ หนึ่งเดียว ไม่มีความกำกวม นั่นคือ "D" ใน DFA
Traffic Light — a 3-state DFAไฟจราจร — DFA 3 states
💡
The big insight: Any domain object that "has a lifecycle" is already an FSM — you're just not writing it down. An Order, a UserAccount, a Subscription, a TCP connection all follow this pattern. Making the FSM explicit lets you encode it in the type system. ข้อสังเกตสำคัญ: object ที่ "มี lifecycle" ทุกตัวคือ FSM อยู่แล้ว — แค่ยังไม่ได้เขียนออกมา Order, UserAccount, Subscription, TCP connection ล้วนเป็น FSM การทำให้ FSM ชัดเจนช่วยให้เราแปลงมันเป็น type system ได้

🐛 Data Clumps — The Code SmellData Clumps — Code Smell ที่พบบ่อย

From Martin Fowler's Refactoring: a Data Clump is when 3 or more fields or parameters always appear together across multiple places, but have never been given their own named type. จาก Martin Fowler ใน Refactoring: Data Clump คือเมื่อ field หรือ parameter 3 ตัวขึ้นไปปรากฏด้วยกันในหลายที่ แต่ยังไม่เคยถูกตั้งชื่อเป็น type ของตัวเอง

3 Classic Clump Patterns3 รูปแบบ Clump ที่พบบ่อย
📦
Loose Parameter ClumpParameter ที่เดินทางด้วยกันเสมอ
Fields always passed together: startDate, endDate or host, port, timeout. Easy to swap order, validation is duplicated everywhere. field ที่ส่งด้วยกันเสมอ เช่น startDate, endDate หรือ host, port, timeout — สลับลำดับได้ง่าย validation กระจาย
🚩
Boolean Flag ExplosionBoolean Flag ระเบิด
Multiple boolean flags representing mutually exclusive states: isActive, isSuspended, isDeleted. 3 bools = 8 combinations — but only 3 are valid. 5 are bugs waiting to happen. boolean หลายตัวแทน state ที่ exclusive กัน: isActive, isSuspended, isDeleted — 3 bool = 8 combinations แต่ valid แค่ 3 ที่เหลือคือ bug รอระเบิด
❓
Nullable Sentinelค่า Null แทนความหมายหลายอย่าง
nil / null used as a sentinel for "not present", "not loaded", or "error" all at once. Ambiguous — callers can't tell the difference. nil ใช้แทนทั้ง "ไม่มีค่า", "ยังไม่โหลด", "เกิด error" — คนเรียกไม่รู้ความแตกต่าง
⚠️
Why Data Clumps hurt: They scatter validation logic, allow callers to pass fields in the wrong order (both time.Time — compiler won't catch it), and make refactoring painful because the "type" lives in every call site simultaneously. ทำไม Data Clumps ถึงเป็นปัญหา: validation กระจาย, ลำดับ parameter สลับกันได้ (ทั้งคู่เป็น time.Time compiler ไม่จับ), และการ refactor เจ็บปวดเพราะ "type" กระจายอยู่ทุก call site

Product Type (AND — struct)

All fields are present simultaneously. Cardinality = product of all field cardinalities. ทุก field มีค่าพร้อมกัน Cardinality = ผลคูณของ cardinality ทุก field

Exactly one variant is active at a time. Cardinality = sum of all variant cardinalities. มีแค่ variant เดียวที่ active ในแต่ละครั้ง Cardinality = ผลรวมของ cardinality ทุก variant

♻️ Recipe: Data Clumps → ADTsสูตร: Data Clumps → ADTs

Three refactoring patterns, each matching a clump type to an ADT encoding. Every pattern has a before/after code pair. สูตร refactor 3 แบบ แต่ละแบบจับคู่ clump กับ ADT encoding ที่เหมาะสม พร้อม code before/after ทุกแบบ

// Named product types — validation in ONE place
type DateRange struct {
    Start time.Time
    End   time.Time
}

func (d DateRange) Valid() bool    { return d.End.After(d.Start) }
func (d DateRange) Days() float64  { return d.End.Sub(d.Start).Hours() / 24 }
func (d DateRange) Contains(t time.Time) bool {
    return !t.Before(d.Start) && !t.After(d.End)
}

type Guest struct {
    Name  string
    Email string
}

func (g Guest) Valid() bool {
    return g.Name != "" && strings.Contains(g.Email, "@")
}

// Clean, self-documenting signatures
func BookRoom(period DateRange, guest Guest) error {
    if !period.Valid() { return errors.New("invalid date range") }
    if !guest.Valid()  { return errors.New("invalid guest") }
    return nil
}

func CalcPrice(period DateRange, roomType string) float64 {
    return period.Days() * rateFor(roomType) // reuse the Days() method
}
// Named product types
interface DateRange {
  start: Date
  end:   Date
}

// Companion functions (no class needed)
const DateRange = {
  valid:    (d: DateRange): boolean => d.end > d.start,
  days:     (d: DateRange): number  => (d.end.getTime() - d.start.getTime()) / 86_400_000,
  contains: (d: DateRange, t: Date): boolean => t >= d.start && t <= d.end,
}

interface Guest { name: string; email: string }
const Guest = {
  valid: (g: Guest): boolean => g.name !== '' && g.email.includes('@'),
}

function bookRoom(period: DateRange, guest: Guest): void {
  if (!DateRange.valid(period)) throw new Error("invalid date range")
  if (!Guest.valid(guest))     throw new Error("invalid guest")
}

function calcPrice(period: DateRange, roomType: string): number {
  return DateRange.days(period) * rateFor(roomType)
}

Pattern B — Boolean flag explosion → Sum TypeBoolean flag ระเบิด → Sum Type

pattern_b.go
// ── BEFORE: 3 booleans = 8 combinations, only 3 are valid ──────────────────
type User struct {
    ID          string
    IsActive    bool // could be true at same time as IsSuspended — bug!
    IsSuspended bool
    IsDeleted   bool
}

func (u User) CanLogin() bool {
    return u.IsActive && !u.IsSuspended && !u.IsDeleted // forget one → security bug
}

// ── AFTER: Sum Type — exactly 3 valid states ────────────────────────────────
type AccountStatus int

const (
    Active    AccountStatus = iota // 0 — default
    Suspended                      // 1 — violated terms
    Deleted                        // 2 — soft-deleted
)

type User struct {
    ID     string
    Status AccountStatus // only 3 values possible
}

func (u User) CanLogin() bool { return u.Status == Active } // simple and correct
// ── BEFORE ────────────────────────────────────────────────────────────────────
interface User {
  id:          string
  isActive:    boolean
  isSuspended: boolean
  isDeleted:   boolean
  // 5 combinations are invalid — compiler won't catch them
}

// ── AFTER: discriminated union ────────────────────────────────────────────────
type AccountStatus = 'active' | 'suspended' | 'deleted'

interface User {
  id:     string
  status: AccountStatus // exactly 3 values
}

function canLogin(u: User): boolean { return u.status === 'active' }

// TypeScript will error if you miss a case:
function statusLabel(s: AccountStatus): string {
  switch (s) {
    case 'active':    return 'Active'
    case 'suspended': return 'Suspended'
    case 'deleted':   return 'Deleted'
    // exhaustive — no default needed; TS errors if a case is missing
  }
}

Pattern C — Nullable sentinel → Option[T]ค่า Null ที่กำกวม → Option[T]

pattern_c.go
// ── BEFORE: nil has multiple meanings — ambiguous ─────────────────────────
type Cart struct {
    Items    []Item
    Discount *float64 // nil = no discount? or "not yet loaded"? or error?
    CouponID *string  // nil = no coupon? or invalid coupon?
}

func ApplyDiscount(cart Cart) float64 {
    total := calcTotal(cart.Items)
    if cart.Discount != nil { // easy to forget this nil check
        total *= (1 - *cart.Discount)
    }
    return total
}

// ── AFTER: Option[T] — explicit, unambiguous ────────────────────────────────
type Option[T any] struct{ v *T }

func Some[T any](val T) Option[T]  { return Option[T]{v: &val} }
func None[T any]() Option[T]       { return Option[T]{} }
func (o Option[T]) Present() bool  { return o.v != nil }
func (o Option[T]) Unwrap() (T, bool) {
    if o.v == nil { var zero T; return zero, false }
    return *o.v, true
}
func (o Option[T]) OrElse(fallback T) T {
    if v, ok := o.Unwrap(); ok { return v }
    return fallback
}

type Cart struct {
    Items    []Item
    Discount Option[float64] // Some(0.15) = 15% off; None() = no discount
    CouponID Option[string]  // explicit, no ambiguity
}

func ApplyDiscount(cart Cart) float64 {
    total := calcTotal(cart.Items)
    discount := cart.Discount.OrElse(0.0) // safe, no nil panic
    return total * (1 - discount)
}
// ── BEFORE ────────────────────────────────────────────────────────────────────
interface Cart {
  items:    Item[]
  discount: number | null   // null = "no discount"? "not loaded"?
  couponId: string | null   // ambiguous
}

// ── AFTER: discriminated Option type ──────────────────────────────────────────
type Option = { kind: 'none' } | { kind: 'some'; value: T }

const none  = (): Option         => ({ kind: 'none' })
const some  = (value: T): Option => ({ kind: 'some', value })
const orElse = (o: Option, fallback: T): T =>
  o.kind === 'some' ? o.value : fallback

interface Cart {
  items:    Item[]
  discount: Option  // Some(0.15) = 15% off; none() = no discount
  couponId: Option
}

function applyDiscount(cart: Cart): number {
  const total    = calcTotal(cart.items)
  const discount = orElse(cart.discount, 0)
  return total * (1 - discount)
}
🚀
The refactoring move is always the same: (1) find fields that travel together, (2) give them a name, (3) move validation inside, (4) replace all call sites. The ADT encoding follows automatically from whether the fields are AND (product) or OR (sum). ขั้นตอน refactor เหมือนกันเสมอ: (1) หา field ที่เดินทางด้วยกัน (2) ตั้งชื่อ (3) ย้าย validation เข้าไปข้างใน (4) แก้ทุก call site จะเป็น product หรือ sum type ขึ้นอยู่กับว่า field เป็นแบบ AND หรือ OR

🏗️ Encoding FSM as Sum Typesแปลง FSM เป็น Sum Types

The design process: first draw the FSM, then mechanically translate each state to a type and each transition to a function. The compiler then enforces the FSM's rules for free. กระบวนการออกแบบ: วาด FSM ก่อน แล้ว mechanically แปลงแต่ละ state เป็น type และแต่ละ transition เป็น function จากนั้น compiler รับผิดชอบบังคับกฎของ FSM แทนเรา

4-Step Recipeสูตร 4 ขั้นตอน
✏️
1. Draw states1. วาด States
List every state the system can be in as bubbles. Name them clearly.ระบุทุก state ที่ระบบเป็นได้ วาดเป็นวงกลม ตั้งชื่อให้ชัด
🧱
2. Each state → a type2. แต่ละ State → type
Each state becomes its own struct/type carrying only the data available in that state.แต่ละ state กลายเป็น struct ของตัวเอง เก็บเฉพาะข้อมูลที่มีในสถานะนั้น
➡️
3. Transitions → functions3. Transitions → functions
Each arrow in the FSM becomes a function: func (current StateA) event() StateB. Return type encodes the destination.แต่ละลูกศรใน FSM กลายเป็น function: func (StateA) event() StateB — return type บังคับ destination
🔒
4. Compiler enforces FSM4. Compiler บังคับ FSM
Calling a non-existent transition (e.g. cancel(deliveredOrder)) is a compile error — not a runtime panic.การเรียก transition ที่ไม่มีอยู่ (เช่น cancel ออเดอร์ที่ส่งแล้ว) คือ compile error ไม่ใช่ runtime panic
Order Lifecycle FSMFSM ของ Order Lifecycle
order_fsm.go — FSM encoded as Go sum typeFSM แปลงเป็น Go sum type
package order

import "time"

// ── Step 2: Each state is its own type ──────────────────────────────────────
// Only the data meaningful in that state is carried.

type PendingOrder struct {
    ID    string
    Items []Item
}

type ConfirmedOrder struct {
    ID          string
    Items       []Item
    ConfirmedAt time.Time
}

type ShippedOrder struct {
    ID           string
    TrackingCode string
    Carrier      string
}

type DeliveredOrder struct {
    ID          string
    DeliveredAt time.Time
}

type CancelledOrder struct {
    ID     string
    Reason string
}

// ── Step 3: Transitions as pure functions ────────────────────────────────────
// The function signature IS the FSM edge: (current state) → (next state)

func (o PendingOrder) Confirm() ConfirmedOrder {
    return ConfirmedOrder{ID: o.ID, Items: o.Items, ConfirmedAt: time.Now()}
}

func (o PendingOrder) Cancel(reason string) CancelledOrder {
    return CancelledOrder{ID: o.ID, Reason: reason}
}

func (o ConfirmedOrder) Ship(tracking, carrier string) ShippedOrder {
    return ShippedOrder{ID: o.ID, TrackingCode: tracking, Carrier: carrier}
}

func (o ConfirmedOrder) Cancel(reason string) CancelledOrder {
    return CancelledOrder{ID: o.ID, Reason: reason}
}

func (o ShippedOrder) Deliver() DeliveredOrder {
    return DeliveredOrder{ID: o.ID, DeliveredAt: time.Now()}
}

// ── There is no CancelledOrder.Cancel() or DeliveredOrder.Cancel() ──────────
// Calling order.Cancel() on a ShippedOrder is a COMPILE ERROR — not a runtime panic.

// ── Step 4: Sum type = "any Order" ──────────────────────────────────────────
type Order interface{ orderState() }

func (PendingOrder)   orderState() {}
func (ConfirmedOrder) orderState() {}
func (ShippedOrder)   orderState() {}
func (DeliveredOrder) orderState() {}
func (CancelledOrder) orderState() {}

// Exhaustive type switch — Go will panic on default if a case is missing
func PrintStatus(o Order) string {
    switch v := o.(type) {
    case PendingOrder:   return "Pending: " + fmt.Sprintf("%d items", len(v.Items))
    case ConfirmedOrder: return "Confirmed at " + v.ConfirmedAt.Format(time.RFC3339)
    case ShippedOrder:   return "Shipped: " + v.TrackingCode + " via " + v.Carrier
    case DeliveredOrder: return "Delivered: " + v.DeliveredAt.Format(time.RFC3339)
    case CancelledOrder: return "Cancelled: " + v.Reason
    default:             panic("unreachable — new state added without updating PrintStatus")
    }
}
// ── Step 2: Each state is a variant of the discriminated union ───────────────
type Order =
  | { status: 'pending';   id: string; items: Item[] }
  | { status: 'confirmed'; id: string; items: Item[]; confirmedAt: Date }
  | { status: 'shipped';   id: string; trackingCode: string; carrier: string }
  | { status: 'delivered'; id: string; deliveredAt: Date }
  | { status: 'cancelled'; id: string; reason: string }

// Convenience aliases
type Pending   = Extract
type Confirmed = Extract
type Shipped   = Extract

// ── Step 3: Transitions as typed functions ───────────────────────────────────
function confirm(o: Pending): Confirmed {
  return { status: 'confirmed', id: o.id, items: o.items, confirmedAt: new Date() }
}

function ship(o: Confirmed, trackingCode: string, carrier: string): Shipped {
  return { status: 'shipped', id: o.id, trackingCode, carrier }
}

function deliver(o: Shipped): Extract {
  return { status: 'delivered', id: o.id, deliveredAt: new Date() }
}

// cancel only accepts Pending | Confirmed — cannot call on Shipped or Delivered
function cancel(o: Pending | Confirmed, reason: string): Extract {
  return { status: 'cancelled', id: o.id, reason }
}

// ── Step 4: Exhaustive switch — TypeScript errors on missing cases ────────────
function printStatus(o: Order): string {
  switch (o.status) {
    case 'pending':   return `Pending: ${o.items.length} items`
    case 'confirmed': return `Confirmed at ${o.confirmedAt.toISOString()}`
    case 'shipped':   return `Shipped: ${o.trackingCode} via ${o.carrier}`
    case 'delivered': return `Delivered: ${o.deliveredAt.toISOString()}`
    case 'cancelled': return `Cancelled: ${o.reason}`
    // TS will show an error here if you add a new variant and forget this switch
  }
}

💻 Full Example: TCP Connection FSMตัวอย่างเต็ม: TCP Connection FSM

TCP connections follow a well-known state machine. Here we show the contrast between an untyped string-state approach (runtime bugs) and a fully encoded ADT approach (compile-time safety). TCP connection มี state machine ที่มีชื่อเสียง ที่นี่เราแสดงความแตกต่างระหว่าง string-state ที่ไม่มี type (bugs เวลา runtime) กับ ADT ที่ encode เต็ม (safety ตั้งแต่ compile time)

tcp_naive.go — without encoding (runtime bugs)ไม่มี encoding (bugs เวลา runtime)
// The naive approach — state stored as a string
type Conn struct {
    state      string // "closed" | "connecting" | "established" | "closing"
    remoteAddr string
    localPort  int
}

func (c *Conn) Dial(addr string) error {
    if c.state != "closed" {
        return errors.New("already connected")  // easy to forget this guard
    }
    c.remoteAddr = addr
    c.state = "connecting"
    return nil
}

func (c *Conn) Send(data []byte) error {
    if c.state != "established" {  // if you forget this guard → nil-deref crash
        return errors.New("not connected")
    }
    // send data...
    return nil
}

// Problems:
//   c.state = "establihsed"   // typo — compiles, silently breaks Send()
//   c.Send(data)              // called on a Conn{state:"closed"} — only fails at runtime
//   No compile-time guarantee that state transitions are valid
// Naive: state stored as string
class Conn {
  private state: string = 'closed'  // any string accepted — typos compile fine
  private remoteAddr = ''

  dial(addr: string): void {
    if (this.state !== 'closed') throw new Error('already connected')
    this.remoteAddr = addr
    this.state = 'connecting'
  }

  send(data: Uint8Array): void {
    if (this.state !== 'established') throw new Error('not connected')
    // send...
  }

tcp_typed.go — with FSM encoding (compile-time safety)มี FSM encoding (safety ตั้งแต่ compile time)
package tcp

import (
    "errors"
    "net"
)

// ── States — each carries only the data relevant to that state ───────────────

type Closed struct{} // no data — a Closed connection is just closed

type Connecting struct {
    RemoteAddr string
}

type Established struct {
    RemoteAddr string
    LocalPort  int
    conn       net.Conn // actual network connection (private)
}

type Closing struct {
    RemoteAddr string
}

// ── Transitions — signatures ARE the allowed edges ───────────────────────────

// Closed → Connecting
func (Closed) Dial(addr string) (Connecting, error) {
    // resolve address, initiate TCP handshake...
    return Connecting{RemoteAddr: addr}, nil
}

// Connecting → Established (handshake complete)
func (c Connecting) Connected(conn net.Conn) Established {
    return Established{
        RemoteAddr: c.RemoteAddr,
        LocalPort:  conn.LocalAddr().(*net.TCPAddr).Port,
        conn:       conn,
    }
}

// Connecting → Closed (handshake failed)
func (Connecting) Failed() Closed { return Closed{} }

// Established → can send data (only method available in this state!)
func (c Established) Send(data []byte) error {
    _, err := c.conn.Write(data)
    return err
}

// Established → Closing (initiate graceful close)
func (c Established) Close() (Closing, error) {
    if err := c.conn.CloseWrite(); err != nil {
        return Closing{}, err
    }
    return Closing{RemoteAddr: c.RemoteAddr}, nil
}

// Closing → Closed (fully closed)
func (Closing) Done() Closed { return Closed{} }

// ── What you CANNOT do ────────────────────────────────────────────────────────
// var c Closed
// c.Send(data)      // compile error: Closed has no method Send
// c.Close()         // compile error: Closed has no method Close
// c.Connected(conn) // compile error: Closed has no method Connected

// ── Sum type: any connection state ───────────────────────────────────────────
type ConnState interface{ connState() }

func (Closed)      connState() {}
func (Connecting)  connState() {}
func (Established) connState() {}
func (Closing)     connState() {}

// The type switch is exhaustive — add a state, forget to handle it → panic at startup
func Describe(s ConnState) string {
    switch v := s.(type) {
    case Closed:      return "closed"
    case Connecting:  return "connecting to " + v.RemoteAddr
    case Established: return fmt.Sprintf("established (port %d)", v.LocalPort)
    case Closing:     return "closing " + v.RemoteAddr
    default:          panic("unhandled TCP state")
    }
}
// ── States ────────────────────────────────────────────────────────────────────
type Closed      = { status: 'closed' }
type Connecting  = { status: 'connecting';   remoteAddr: string }
type Established = { status: 'established';  remoteAddr: string; localPort: number }
type Closing     = { status: 'closing';      remoteAddr: string }

type ConnState = Closed | Connecting | Established | Closing

// ── Transitions ──────────────────────────────────────────────────────────────
function dial(s: Closed, addr: string): Connecting {
  return { status: 'connecting', remoteAddr: addr }
}

function connected(s: Connecting, port: number): Established {
  return { status: 'established', remoteAddr: s.remoteAddr, localPort: port }
}

function failed(s: Connecting): Closed { return { status: 'closed' } }

// send() only accepts Established — calling it on Closed is a TypeScript error
function send(s: Established, data: Uint8Array): void {
  // actual send...
}

function close(s: Established): Closing {
  return { status: 'closing', remoteAddr: s.remoteAddr }
}

function done(s: Closing): Closed { return { status: 'closed' } }

// ── Exhaustive switch ─────────────────────────────────────────────────────────
function describe(s: ConnState): string {
  switch (s.status) {
    case 'closed':      return 'closed'
    case 'connecting':  return `connecting to ${s.remoteAddr}`
    case 'established': return `established (port ${s.localPort})`
    case 'closing':     return `closing ${s.remoteAddr}`
    // TS errors here if you add a new state variant and forget to handle it
  }
}

What the compiler now guarantees: You cannot call send() on a Closed connection. You cannot call dial() on an Established connection. No nil checks needed. No typo-in-state-string bugs. If you add a new state, every switch/type-assert in the codebase shows a compile error until you handle it. สิ่งที่ compiler รับประกัน: ไม่สามารถ send() บน Closed connection ได้ ไม่สามารถ dial() บน Established ได้ ไม่ต้อง nil check ไม่มี bug จาก typo ใน string state ถ้าเพิ่ม state ใหม่ ทุก switch ในโค้ดจะ compile error จนกว่าจะ handle ครบ
