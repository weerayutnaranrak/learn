🏗️ K8s Architecture (Step 2)

K8s cluster ประกอบด้วย 2 ส่วนหลัก: Control Plane (สมอง) ที่ตัดสินใจทุกอย่าง และ Worker Nodes (แขน) ที่รัน workload จริง

☸️ Control Plane Components
⚙️ kube-apiserver
Frontend ของ Control Plane — รับทุก REST request จาก kubectl, controllers, nodes แล้วเก็บ state ลง etcd | Port 6443 (HTTPS)
🗄️ etcd
Distributed key-value store — เก็บ cluster state ทั้งหมด (desired state) เช่น configs, secrets, pod specs | ต้อง backup เสมอ
📅 kube-scheduler
ดู Pods ที่ยังไม่มี Node → เลือก Node ที่เหมาะสมโดยดู resource requests, node affinity, taints/tolerations
🎛️ kube-controller-manager
รัน control loops หลายตัว: ReplicaSet Controller (รักษาจำนวน replicas), Deployment, Node, ServiceAccount, Endpoint controllers
🖥️ Worker Node Components
🤖 kubelet
Agent บน Node แต่ละตัว — รับ PodSpec จาก API Server แล้วสั่ง container runtime ให้รัน/หยุด container ตาม spec | รายงาน status กลับ
🔀 kube-proxy
รักษา network rules (iptables/IPVS) บน node — ทำให้ Service IP ทำงานได้ โดย forward traffic ไปยัง Pods ที่ถูกต้อง
🐳 Container Runtime
รันตัว container จริง — containerd (default ใน K8s 1.20+) หรือ CRI-O | Docker ถูกเอาออกจาก K8s 1.24 แล้ว
📦 Pods
หน่วยที่เล็กที่สุดที่ K8s จัดการ — container 1+ ตัวที่ share network/storage | ทุก pod มี unique IP ใน cluster

  name: api-pod
  namespace: production
  labels:
    app: api          # selector label — Service ใช้ label นี้ค้นหา Pod
    version: v2
spec:
  containers:
  - name: api
    image: myapp/api:v2.1.0     # ระบุ version เสมอ อย่าใช้ :latest ใน production
    ports:
    - containerPort: 8080
    env:

      valueFrom:
        configMapKeyRef:          # อ่านจาก ConfigMap
          name: app-config
          key: db_host
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:             # อ่านจาก Secret
          name: app-secret
          key: db_password
    resources:
      requests:                   # minimum ที่ต้องการ (scheduler ใช้จัดสรร Node)
        memory: "64Mi"
        cpu: "100m"               # 100m = 0.1 CPU core
      limits:                     # maximum ที่อนุญาต (OOMKill ถ้าเกิน memory)
        memory: "256Mi"
        cpu: "500m"
    livenessProbe:                # K8s restart Pod ถ้า probe นี้ fail
      httpGet:
        path: /healthz
        port: 8080
      initialDelaySeconds: 10
      periodSeconds: 10
    readinessProbe:               # Pod รับ traffic ได้เมื่อ probe นี้ pass
      httpGet:
        path: /ready
        port: 8080
      initialDelaySeconds: 5
      periodSeconds: 5

kind: Deployment

🌐 Networking — Services & Ingress (Step 4)

Pods มี IP ชั่วคราว — เมื่อ Pod ตายแล้วสร้างใหม่ IP เปลี่ยน ดังนั้นต้องใช้ Service เป็น stable endpoint และ Ingress สำหรับ HTTP routing จากภายนอก

🔵 ClusterIP
Internal IP ที่ใช้ได้เฉพาะภายใน cluster — default type เหมาะกับ internal microservice communication
Internal only
🟢 NodePort
เปิด port บน Node ทุกตัว (30000–32767) ให้ access จากภายนอก cluster ได้ — ใช้สำหรับ dev/testing
Dev/Testing
🟡 LoadBalancer
Provision cloud load balancer (AWS ALB, GCP LB) — มี external IP จริง เหมาะ production แต่แพง
Production
🟣 Ingress
HTTP/HTTPS router — 1 LoadBalancer รองรับหลาย services ด้วย path/host rules ประหยัดกว่ามาก
HTTP routing 
apiVersion: v1
kind: Service
metadata:
  name: api-service
  namespace: production
spec:
  type: ClusterIP           # default — internal only
  selector:
    app: api                # forward traffic ไปยัง Pods ที่มี label app=api
  ports:
  - name: http
    port: 80                # port ที่ Service listen
    targetPort: 8080        # port ที่ Pod รับ

# DNS ภายใน cluster:
# api-service.production.svc.cluster.local:80
# หรือย่อแค่ api-service ถ้าอยู่ namespace เดียวกัน

apiVersion: v1

💾 Storage — PV, PVC, StorageClass (Step 6)

Storage Concepts
💽
PersistentVolume (PV)
Storage ที่ admin provision ไว้แล้ว หรือ dynamic provision — เป็น cluster resource เหมือน Node (ไม่ผูกกับ namespace)
  • accessModes: RWO, ROX, RWX
  • reclaimPolicy: Retain/Delete
  • storageClassName ระบุ type
📋
PersistentVolumeClaim (PVC)
Request สำหรับ storage จาก Pod — ระบุขนาดและ access mode K8s จะ bind PVC กับ PV ที่เหมาะสม
  • Pod อ้างถึง PVC ไม่ใช่ PV โดยตรง
  • PVC ผูกกับ namespace
  • Bound 1:1 กับ PV
🏭
StorageClass
Template สำหรับสร้าง PV อัตโนมัติ (Dynamic Provisioning) — ระบุ provisioner เช่น EBS, GCE-PD, NFS
  • Dynamic provisioning
  • ระบุ disk type (SSD/HDD)
  • default StorageClass ใน cluster
storage.yaml — StorageClass + PVC + Pod
# StorageClass — ให้ K8s สร้าง disk อัตโนมัติบน AWS
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
  iops: "3000"
  throughput: "125"
reclaimPolicy: Delete          # ลบ EBS volume เมื่อ PVC ถูกลบ
volumeBindingMode: WaitForFirstConsumer  # สร้าง volume ใน AZ เดียวกับ Pod

---
# PersistentVolumeClaim — request storage 10GB
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
  namespace: production
spec:
  accessModes:
  - ReadWriteOnce              # 1 node อ่าน+เขียนพร้อมกัน (ส่วนใหญ่ใช้อันนี้)
  storageClassName: fast-ssd
  resources:
    requests:
      storage: 10Gi

---
# Pod ใช้ PVC
apiVersion: v1
kind: Pod
metadata:
  name: postgres-pod
spec:
  containers:
  - name: postgres
    image: postgres:16
    volumeMounts:
    - name: data
      mountPath: /var/lib/postgresql/data
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: postgres-data   # อ้างถึง PVC ที่สร้างไว้

📈 Scaling & Updates (Step 7–8)

Scaling Strategies
⚡
HPA — Horizontal Pod Autoscaler
เพิ่ม/ลด จำนวน Pod replicas อัตโนมัติตาม CPU/Memory/Custom metrics — ส่วนใหญ่ใช้อันนี้
Scale replicas CPU/Memory
📐
VPA — Vertical Pod Autoscaler
ปรับ resource requests/limits ของ Pod อัตโนมัติ — ดีสำหรับหาค่า optimal ต้อง restart Pod เมื่อปรับ
Resize resources Restart required
🖥️
Cluster Autoscaler
เพิ่ม/ลด จำนวน Node ใน cluster — ทำงานร่วมกับ cloud provider เพื่อ provision/terminate VMs อัตโนมัติ
Scale nodes Cloud integration
hpa.yaml — Horizontal Pod Autoscaler
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-hpa
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-deployment
  minReplicas: 2              # ขั้นต่ำ 2 pods เสมอ (HA)
  maxReplicas: 20             # ขยายได้สูงสุด 20 pods
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70   # scale out เมื่อ avg CPU > 70%
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300   # รอ 5 นาทีก่อน scale down (ป้องกัน flapping)
      policies:
      - type: Percent
        value: 10
        periodSeconds: 60              # ลดได้ไม่เกิน 10% ต่อนาที
    scaleUp:
      stabilizationWindowSeconds: 30
      policies:
      - type: Percent
        value: 100
        periodSeconds: 30              # เพิ่มได้ 100% ต่อ 30 วินาที (scale up เร็ว)
Deployment Strategies
🔄
Rolling Update
แทนที่ Pods ทีละน้อย — zero downtime, rollback ได้ทันที เหมาะกับส่วนใหญ่
  • maxSurge: 1 (เพิ่มได้)
  • maxUnavailable: 0 (ห้ามหาย)
  • kubectl rollout undo
Default
🔵🟢
Blue-Green Deploy
รัน 2 environments พร้อมกัน สลับ traffic ทันที — rollback เร็ว แต่ใช้ resource 2x
  • สลับผ่าน Service selector
  • Test green ก่อน switch
  • ลบ blue หลัง confirm
Instant switch
🐤
Canary Deploy
ส่ง traffic บางส่วน (5-10%) ไปยัง version ใหม่ก่อน ดู metrics แล้วค่อยขยาย — ลด risk
  • ใช้ Ingress weight หรือ Istio
  • Monitor error rate
  • Gradual traffic shift
Low risk

import (
	"database/sql"
	"encoding/json"
	"net/http"
	"time"
)

// K8s ใช้ 2 endpoints นี้ตรวจสุขภาพ app:
// - /healthz  → livenessProbe  (K8s restart Pod ถ้า fail)
// - /ready    → readinessProbe (K8s หยุดส่ง traffic ถ้า fail)

type HealthHandler struct {
	db        *sql.DB
	startTime time.Time
}

func NewHealthHandler(db *sql.DB) *HealthHandler {
	return &HealthHandler{db: db, startTime: time.Now()}
}

// /healthz — ตอบแค่ว่า process ยังรันอยู่ไหม (ง่ายๆ)
func (h *HealthHandler) Liveness(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(map[string]string{
		"status": "ok",
		"uptime": time.Since(h.startTime).String(),
	})
}

// /ready — ตรวจว่าพร้อมรับ traffic จริงๆ (ตรวจ dependencies)
func (h *HealthHandler) Readiness(w http.ResponseWriter, r *http.Request) {
	// ตรวจ database connection
	if err := h.db.PingContext(r.Context()); err != nil {
		http.Error(w, `{"status":"not ready","reason":"db unreachable"}`, 503)
		return
	}
	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(map[string]string{"status": "ready"})
}

  const startTime = Date.now();

  // /healthz — ตอบแค่ว่า process ยังรันอยู่ไหม
  router.get('/healthz', (_req: Request, res: Response) => {

  });

controller-runtime — วิธีที่นิยมมากที่สุดสำหรับ Operator
Library ที่ kubebuilder และ operator-sdk ใช้ — ง่ายกว่า raw client-go มาก เพราะ abstract complexity ออกไปเยอะ
🧠
Reconciler Pattern คืออะไร?
แทนที่จะ react กับ events (Added/Modified/Deleted) เหมือน client-go — controller-runtime ให้คุณเขียนแค่ฟังก์ชัน Reconcile() เดียว ที่รับ "ชื่อ object" แล้วทำให้ current state = desired state
K8s จะ call Reconcile() ให้เองเมื่อมี event เกิดขึ้น — ง่ายกว่ามาก ไม่ต้องคิดเรื่อง event types เลย
❌ client-go style (ยาก)
1. ลงทะเบียน AddFunc, UpdateFunc, DeleteFunc
2. รับ object เต็มๆ ต้องตรวจ event type เอง
3. Handle race conditions, retries เอง
4. Manage informers, caches เอง
5. Code เยอะ, bug ง่าย
✅ controller-runtime style (ง่าย)
1. เขียนแค่ Reconcile() function เดียว
2. รับแค่ชื่อ object → ดึง state เอง
3. Return error = retry อัตโนมัติ
4. Library จัดการ informer/cache ให้
5. Code น้อย, อ่านง่าย

package operator

// go get sigs.k8s.io/controller-runtime@latest

import (
	"context"
	"fmt"

	appsv1 "k8s.io/api/apps/v1"
	corev1 "k8s.io/api/core/v1"
	"k8s.io/apimachinery/pkg/api/errors"
	"k8s.io/apimachinery/pkg/runtime"
	"k8s.io/apimachinery/pkg/types"
	ctrl "sigs.k8s.io/controller-runtime"
	"sigs.k8s.io/controller-runtime/pkg/client"
	"sigs.k8s.io/controller-runtime/pkg/log"
)

// DeploymentReconciler — ดูแล Deployments ให้มี annotation "monitored=true" เสมอ
// นี่คือตัวอย่าง Operator อย่างง่าย
type DeploymentReconciler struct {
	client.Client            // embed client — ใช้ r.Get(), r.Update() ได้ทันที
	Scheme *runtime.Scheme
}

// Reconcile — K8s จะ call ฟังก์ชันนี้เมื่อ Deployment มีการเปลี่ยนแปลง
// หน้าที่: ทำให้ "สภาพจริง" ตรงกับ "สภาพที่ต้องการ"
func (r *DeploymentReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
	logger := log.FromContext(ctx)

	// ──────────────────────────────────────────
	// Step 1: ดึง object จาก cluster
	// req.NamespacedName = namespace + name ของ Deployment ที่ trigger
	// ──────────────────────────────────────────
	var deploy appsv1.Deployment
	if err := r.Get(ctx, req.NamespacedName, &deploy); err != nil {
		if errors.IsNotFound(err) {
			// Object ถูกลบแล้ว — ไม่ต้องทำอะไร
			return ctrl.Result{}, nil
		}
		return ctrl.Result{}, fmt.Errorf("get deployment: %w", err)
	}

	// ──────────────────────────────────────────
	// Step 2: ตรวจ desired state vs current state
	// ──────────────────────────────────────────
	needsUpdate := false

	if deploy.Annotations == nil {
		deploy.Annotations = make(map[string]string)
	}

	// ต้องการ: annotation "monitored=true" ต้องมีเสมอ
	if deploy.Annotations["monitored"] != "true" {
		deploy.Annotations["monitored"] = "true"
		needsUpdate = true
		logger.Info("Adding monitored annotation", "deployment", deploy.Name)
	}

	// ต้องการ: replicas ต้องไม่ต่ำกว่า 2 (HA)
	if deploy.Spec.Replicas != nil && *deploy.Spec.Replicas < 2 {
		min := int32(2)
		deploy.Spec.Replicas = &min
		needsUpdate = true
		logger.Info("Enforcing minimum replicas", "deployment", deploy.Name)
	}

	// ──────────────────────────────────────────
	// Step 3: อัพเดทถ้าจำเป็น
	// ──────────────────────────────────────────
	if needsUpdate {
		if err := r.Update(ctx, &deploy); err != nil {
			// Return error = controller-runtime จะ retry อัตโนมัติ
			return ctrl.Result{}, fmt.Errorf("update deployment: %w", err)
		}
	}

	// ctrl.Result{} = สำเร็จ ไม่ต้อง requeue
	// ctrl.Result{RequeueAfter: time.Minute} = requeue หลัง 1 นาที
	return ctrl.Result{}, nil
}

// SetupWithManager — บอก controller-runtime ว่าให้ watch resource ไหน
func (r *DeploymentReconciler) SetupWithManager(mgr ctrl.Manager) error {
	return ctrl.NewControllerManagedBy(mgr).
		For(&appsv1.Deployment{}).   // watch Deployment objects
		Owns(&corev1.Pod{}).          // watch Pods ที่ Deployment เป็น owner
		Complete(r)
}

	"log"

	appsv1 "k8s.io/api/apps/v1"

	"k8s.io/apimachinery/pkg/runtime"
	ctrl "sigs.k8s.io/controller-runtime"
	"sigs.k8s.io/controller-runtime/pkg/log/zap"

	"myapp/operator"
)

func main() {
	// Setup logger
	ctrl.SetLogger(zap.New(zap.UseDevMode(true)))

	// สร้าง scheme — บอกว่าเรารู้จัก resource types ไหน
	scheme := runtime.NewScheme()
	appsv1.AddToScheme(scheme)
	corev1.AddToScheme(scheme)

	// สร้าง Manager — จัดการ kubeconfig, leader election, metrics
	mgr, err := ctrl.NewManager(ctrl.GetConfigOrDie(), ctrl.Options{
		Scheme:                 scheme,
		MetricsBindAddress:     ":8081",
		HealthProbeBindAddress: ":8082",
		LeaderElection:         true,        // HA: 1 replica เป็น leader
		LeaderElectionID:       "my-operator",
	})
	if err != nil {
		log.Fatal("create manager:", err)
	}

	// ลงทะเบียน reconciler
	if err := (&operator.DeploymentReconciler{
		Client: mgr.GetClient(),
		Scheme: mgr.GetScheme(),
	}).SetupWithManager(mgr); err != nil {
		log.Fatal("setup reconciler:", err)
	}

	// Start! — บล็อก process ไว้ (จนกว่าจะ Ctrl+C)
	log.Println("Starting operator...")
	if err := mgr.Start(ctrl.SetupSignalHandler()); err != nil {
		log.Fatal("run manager:", err)
		os.Exit(1)
	}
}

	}
	config, err := clientcmd.BuildConfigFromFlags("", kubeconfig)
	if err != nil {
		log.Fatal(err)
	}

	// 2. สร้าง client
	cs, err := kubernetes.NewForConfig(config)
	if err != nil {
		log.Fatal(err)
	}
	ctx := context.Background()

	// 3. ดึง namespaces ทั้งหมด
	nsList, err := cs.CoreV1().Namespaces().List(ctx, metav1.ListOptions{})
	if err != nil {
		log.Fatal(err)
	}

	// 4. แสดงผลเป็นตาราง
	w := tabwriter.NewWriter(os.Stdout, 0, 0, 3, ' ', 0)
	fmt.Fprintln(w, "NAMESPACE\tPODS\tRUNNING\tPENDING\tFAILED")
	fmt.Fprintln(w, "---------\t----\t-------\t-------\t------")

	for _, ns := range nsList.Items {
		pods, err := cs.CoreV1().Pods(ns.Name).List(ctx, metav1.ListOptions{})
		if err != nil {
			continue
		}
		var running, pending, failed int
		for _, p := range pods.Items {
			switch p.Status.Phase {
			case "Running":
				running++
			case "Pending":
				pending++
			case "Failed":
				failed++
			}
		}
		fmt.Fprintf(w, "%s\t%d\t%d\t%d\t%d\n",
			ns.Name, len(pods.Items), running, pending, failed)
	}
	w.Flush()
}

🔄 ArgoCD — GitOps Continuous Delivery

GitOps คือแนวคิดที่ Git repository เป็น "source of truth" ของ cluster state — ArgoCD จะ monitor Git และ sync cluster ให้ตรงกับ repo โดยอัตโนมัติ ถ้า someone แก้ cluster โดยตรง ArgoCD จะ detect แล้ว revert กลับ

❌ วิธีเก่า — Push-based
1. Developer push code → CI build image
2. CI pipeline รัน kubectl apply โดยตรง
3. ต้องให้ CI มี kubeconfig (security risk)
4. ไม่มี drift detection
5. Audit trail กระจัดกระจาย
✅ GitOps — Pull-based (ArgoCD)
1. Developer push code → CI build & push image
2. CI update image tag ใน Git (config repo)
3. ArgoCD detect Git change → sync อัตโนมัติ
4. ArgoCD อยู่ใน cluster (ไม่ต้องให้ CI มี kubeconfig)
5. Full audit trail ใน Git history

กลุ่มของ Applications — กำหนด access control ว่า team ไหนจัดการ app ไหนได้
AppProject CRD RBAC boundary
🔄

กระบวนการเอา Git state → apply ลง cluster ทำได้ทั้ง manual และ auto-sync

# Sync Strategy Options

# ── 1. Manual Sync (production แนะนำ) ─────────────
syncPolicy: {}   # ไม่มี automated = manual เท่านั้น
# ต้อง argocd app sync myapp หรือกด sync ใน UI
# ดีสำหรับ production — review ก่อน apply เสมอ

# ── 2. Auto Sync (staging / dev) ──────────────────
syncPolicy:
  automated:
    prune: false      # ไม่ลบ resource ที่ไม่มีใน Git (conservative)
    selfHeal: false   # ไม่ revert drift (allow manual override)

# ── 3. Auto Sync + Self Heal (full GitOps) ────────
syncPolicy:
  automated:
    prune: true       # ลบ resources ที่ถูกเอาออกจาก Git
    selfHeal: true    # revert ถ้า cluster drift จาก Git
  # ⚠️ selfHeal: true = ห้าม kubectl apply โดยตรง!
  # เพราะ ArgoCD จะ revert ทุก manual change กลับ

# ── Sync Waves — ควบคุมลำดับ deploy ──────────────
# annotate resource ด้วย:
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "-1"  # ลบล่อนก่อน (-1 ก่อน 0 ก่อน 1)
# ตัวอย่าง:
# wave -1: Namespace, CRDs
# wave  0: ConfigMap, Secret (default)
# wave  1: Deployment, StatefulSet
# wave  2: Ingress, HPA

# .github/workflows/deploy.yaml
# GitHub Actions workflow: build → push → update ArgoCD

name: Build and Deploy

on:
  push:
    branches: [main]

env:
  IMAGE: ghcr.io/myorg/myapp

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4

    # 1. Build & push Docker image
    - name: Build Docker image
      run: |
        docker build -t $IMAGE:${{ github.sha }} .
        docker push $IMAGE:${{ github.sha }}
        # tag เป็น latest ด้วย
        docker tag $IMAGE:${{ github.sha }} $IMAGE:latest
        docker push $IMAGE:latest

    # 2. Update config repo (GitOps approach)
    - name: Update image tag in config repo
      run: |
        git clone https://github.com/myorg/k8s-configs config-repo
        cd config-repo

        # อัพเดท image tag ใน values-prod.yaml
        sed -i "s/  tag: .*/  tag: \"${{ github.sha }}\"/" \
          apps/myapp/production/values-prod.yaml

        git config user.email "ci@github.com"
        git config user.name "GitHub Actions"
        git add .
        git commit -m "ci: deploy myapp@${{ github.sha }}"
        git push

    # ArgoCD จะ detect Git change แล้ว sync อัตโนมัติ ✅
    # (ถ้าตั้ง syncPolicy.automated)

    # ── หรือ trigger sync โดยตรงผ่าน ArgoCD API ──────────
    - name: Trigger ArgoCD sync (optional)
      run: |
        curl -s -X POST \
          -H "Authorization: Bearer ${{ secrets.ARGOCD_TOKEN }}" \
          https://argocd.example.com/api/v1/applications/myapp-production/sync

ติดตั้ง ArgoCD บน Cluster

install-argocd.sh — ติดตั้งด้วย kubectl หรือ Helm
# ── วิธีที่ 1: kubectl apply (เร็ว สำหรับทดลอง) ──────────────────
kubectl create namespace argocd
kubectl apply -n argocd \
  -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

# ดู pods
kubectl get pods -n argocd

# รับ initial admin password
kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath="{.data.password}" | base64 -d && echo

# Port-forward เพื่อเข้า UI
kubectl port-forward svc/argocd-server -n argocd 8080:443
# เข้า https://localhost:8080

# ── วิธีที่ 2: Helm (แนะนำสำหรับ production) ─────────────────────
helm repo add argo https://argoproj.github.io/argo-helm
helm repo update

  --namespace argocd \
  --create-namespace \
