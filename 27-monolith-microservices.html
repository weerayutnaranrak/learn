🧱 MonolithMonolith (แบบดั้งเดิม)

All modules live in a single codebase and are deployed as one unit — simple, fast to start, and great for small teams ทุก module รวมอยู่ใน codebase เดียวและ deploy เป็น unit เดียว — เรียบง่าย เริ่มได้เร็ว เหมาะกับทีมขนาดเล็ก

🏗️
Structureโครงสร้าง
All layers in one project, one binary, one DB connectionทุก layer อยู่ในโปรเจกต์เดียว binary เดียว เชื่อม DB เดียว
  • Presentation Layer
  • Business Logic Layer
  • Data Access Layer
  • Single DBDB เดียว
✅
Advantagesข้อดี
  • Simple to develop and debugพัฒนาและ debug ง่าย
  • Low operational overheadต้นทุน ops ต่ำ
  • Easy to test end-to-endทดสอบ end-to-end ง่าย
  • No network latency between modulesไม่มี network latency ระหว่าง module
  • Fast for small teams / MVPเร็วสำหรับทีมเล็กและ MVP
❌
Disadvantagesข้อเสีย
  • Must deploy everything at onceต้อง deploy ทั้งหมดพร้อมกัน
  • Scale all or nothingต้อง scale ทั้งหมด
  • Codebase becomes hard to navigatecodebase ยิ่งใหญ่ยิ่งยากจัดการ
  • One bug can take down the whole appbug หนึ่งล้มทั้งระบบ
  • Tech stack locked for entire appใช้ tech stack เดียวทั้ง app
Monolith — single deployable unitหน่วย deploy เดียว
deploy as 1 binary · 1 process · 1 DB
monolith/main.go 
package main

import (
	"database/sql"
	"encoding/json"
	"log"
	"net/http"

	_ "github.com/lib/pq"
)

// ทุกอย่างอยู่ในโปรเจกต์เดียว: handler + service + repository
var db *sql.DB

type Order struct {
	ID     int     `json:"id"`
	UserID int     `json:"user_id"`
	Total  float64 `json:"total"`
}

// Handler layer
func createOrderHandler(w http.ResponseWriter, r *http.Request) {
	var order Order
	json.NewDecoder(r.Body).Decode(&order)

	// Service logic อยู่ตรงนี้เลย
	if order.Total <= 0 {
		http.Error(w, "invalid total", http.StatusBadRequest)
		return
	}

	// Repository อยู่ตรงนี้เลย
	err := db.QueryRow(
		"INSERT INTO orders(user_id, total) VALUES($1,$2) RETURNING id",
		order.UserID, order.Total,
	).Scan(&order.ID)
	if err != nil {
		http.Error(w, err.Error(), http.StatusInternalServerError)
		return
	}

	json.NewEncoder(w).Encode(order)
}

func main() {
	var err error
	db, err = sql.Open("postgres", "postgres://localhost/shop?sslmode=disable")
	if err != nil {
		log.Fatal(err)
	}

	http.HandleFunc("/orders", createOrderHandler)
	http.HandleFunc("/users", usersHandler)
	http.HandleFunc("/payments", paymentsHandler)
	log.Fatal(http.ListenAndServe(":8080", nil))
}
📦 Modular MonolithModular Monolith

Still one deployable binary, but the codebase is split into well-defined modules that communicate only through interfaces — the best of both worlds for growing teams deploy เป็น binary เดียวเหมือนเดิม แต่แบ่ง codebase เป็น module ที่มีขอบเขตชัดเจน สื่อสารกันผ่าน interface เท่านั้น

🏗️
Structureโครงสร้าง
One binary, modules separated by package boundary with interface contractsbinary เดียว แต่แบ่ง module ด้วยขอบเขต package และ interface
  • internal/order/
  • internal/payment/
  • internal/user/
  • Shared DB (per module schema)DB ร่วม (แยก schema ต่อ module)
✅
Advantagesข้อดี
  • Clear module boundariesขอบเขต module ชัดเจน
  • Easy refactor toward microservices laterrefactor ไปเป็น microservices ได้ง่ายในอนาคต
  • No network overhead — still in-processยังเรียก in-process ไม่มี network latency
  • Low ops complexityops ยังง่าย
  • Better team code ownershipแต่ละทีม own module ได้ชัดเจน
❌
Disadvantagesข้อเสีย
  • Still must deploy all modules togetherยังต้อง deploy พร้อมกันทั้งหมด
  • Shared DB can become a bottleneckshared DB อาจเป็น bottleneck
  • Requires discipline to enforce boundariesต้องวินัยสูงไม่ให้ import ข้าม module
  • Scale all or nothingยัง scale ทั้งหมดหรือไม่ scale
Modular Monolith — one binary, clear module zonesbinary เดียว แต่แบ่ง module ชัดเจน
shop/internal/order/service.go 
package order

import "context"

// Module interface — Payment module เข้าถึงได้แค่นี้
type PaymentModule interface {
	Charge(ctx context.Context, userID int, amount float64) (string, error)
}

type Service struct {
	repo    Repository
	payment PaymentModule // inject ผ่าน interface, ไม่ import package โดยตรง
}

func NewService(repo Repository, payment PaymentModule) *Service {
	return &Service{repo: repo, payment: payment}
}

func (s *Service) CreateOrder(ctx context.Context, userID int, total float64) (*Order, error) {
	// เรียก payment ผ่าน interface ไม่ใช่ HTTP call
	txID, err := s.payment.Charge(ctx, userID, total)
	if err != nil {
		return nil, err
	}

	order := &Order{UserID: userID, Total: total, PaymentTxID: txID}
	return s.repo.Save(ctx, order)
}
shop/cmd/main.go 
// wire ทุก module เข้าด้วยกัน, deploy เป็น binary เดียว
package main

import (
	"shop/internal/order"
	"shop/internal/payment"
	"shop/internal/user"
)

func main() {
	db := connectDB()

	userSvc    := user.NewService(user.NewRepo(db))
	paymentSvc := payment.NewService(payment.NewRepo(db))
	orderSvc   := order.NewService(order.NewRepo(db), paymentSvc) // inject interface

	// ทุก module อยู่ใน process เดียว
	startServer(orderSvc, paymentSvc, userSvc)
}
⚠️ Distributed MonolithDistributed Monolith (Anti-pattern)

Services are split but remain tightly coupled — synchronous chains, shared DB, must deploy together แยก service แล้วแต่ยัง tightly coupled — synchronous chain, shared DB, ต้อง deploy พร้อมกัน

Anti-pattern — What NOT to doสิ่งที่ไม่ควรทำ
This is one of the most common pitfalls when teams migrate from Monolith to Microservices without understanding the principles. You get all the complexity of microservices without any of the benefits. นี่คือหนึ่งในกับดักที่พบบ่อยที่สุดเมื่อทีมย้ายจาก Monolith ไป Microservices โดยไม่เข้าใจหลักการ — ได้รับความซับซ้อนของ microservices ทั้งหมด แต่ไม่ได้ประโยชน์ใดๆ
🚩
Warning Signsสัญญาณเตือน
  • Services must deploy at the same timeservices ต้อง deploy พร้อมกันเสมอ
  • Service A crashes → Service B crashes tooservice A ล้ม → service B ล้มตาม
  • Synchronous HTTP chain A → B → Cเรียก HTTP chain แบบ A → B → C
  • Services share the same databaseservices ใช้ DB เดียวกัน
  • Service knows the DB schema of another serviceservice รู้โครงสร้าง DB ของ service อื่น
  • Breaking change in one service forces all to redeployเปลี่ยน API หนึ่งตัวต้อง redeploy ทุกตัว
💀
Consequencesผลเสีย — Worst of Both Worlds
  • Network latency of microservicesnetwork latency ของ microservices
  • Fragility of monolith (cascade failure)ความเปราะบางของ monolith (cascade failure)
  • Ops complexity — many services to manageops ซับซ้อน — ดูแลหลาย service
  • No independent deployabilityไม่สามารถ deploy อิสระได้จริงๆ
  • Distributed transaction problems without solutionsปัญหา distributed transaction โดยไม่มีทางแก้
Distributed Monolith — tight coupling across process boundariestightly coupled ข้าม process
order-service/main.go 
// ⚠️ Distributed Monolith: Service A call B call C แบบ synchronous chain
// หาก payment-service ล้ม → order-service ล้มตาม → user ไม่ได้รับ notification

func (s *OrderService) CreateOrder(ctx context.Context, req CreateOrderReq) error {
	// Step 1: บันทึก order ใน shared database (ตาราง "orders")
	orderID, err := s.db.InsertOrder(ctx, req) // shared DB!
	if err != nil {
		return err
	}

	// Step 2: synchronous call ไปหา payment-service
	// ถ้า payment-service timeout → order ค้างอยู่ในสถานะ pending ตลอด
	resp, err := http.Post("http://payment-service/charge", "application/json",
		encodeChargeRequest(orderID, req.Amount))
	if err != nil {
		return fmt.Errorf("payment failed: %w", err) // cascade failure
	}
	defer resp.Body.Close()

	// Step 3: synchronous call ไปหา notification-service
	// ต้อง deploy notification-service พร้อม order-service เสมอ
	http.Post("http://notification-service/send", "application/json",
		encodeNotification(req.UserID, orderID))

	return nil
}
🔬 MicroservicesMicroservices

Each service is truly independent — own DB, own deployment lifecycle, communicate via events or API Gateway แต่ละ service อิสระจริงๆ — มี DB ของตัวเอง, deploy lifecycle เป็นอิสระ, สื่อสารผ่าน event หรือ API Gateway

🏗️
Structureโครงสร้าง
Separate services, separate DBs, async event communicationservices แยก, DB แยก, สื่อสารผ่าน event แบบ async
  • API Gateway (single entryจุดเข้าเดียว)
  • DB per Service
  • Message Bus (Kafka)
  • Independent deploydeploy อิสระ
✅
Advantagesข้อดี
  • Deploy each service independentlydeploy แต่ละ service อิสระ
  • Scale only what needs scalingscale เฉพาะ service ที่ต้องการ
  • True fault isolationfault isolation จริงๆ
  • Teams work independently (Conway's Law)ทีมทำงานอิสระจากกัน
  • Different tech per serviceใช้ tech ต่างกันต่อ service ได้
❌
Disadvantagesข้อเสีย
  • High operational complexityops ซับซ้อนมาก
  • Distributed tracing is hardต้องทำ distributed tracing
  • Eventual consistency challengesต้องรับมือ eventual consistency
  • Integration testing is difficultintegration test ยากขึ้น
  • Not suitable for small teamsไม่เหมาะทีมเล็ก
Microservices — independent services, async communicationservice อิสระ, สื่อสาร async
order-service/service.go 
// order-service: อิสระ มี DB ของตัวเอง publish event แทน sync call
package order

import (
	"context"
	"encoding/json"
)

type EventPublisher interface {
	Publish(ctx context.Context, topic string, payload any) error
}

type Service struct {
	repo      Repository
	publisher EventPublisher // Kafka, NATS, etc.
}

func (s *Service) CreateOrder(ctx context.Context, req CreateOrderReq) (*Order, error) {
	order := &Order{
		UserID: req.UserID,
		Total:  req.Total,
		Status: "pending", // รอ payment confirm
	}

	// บันทึกใน DB ของ order-service เท่านั้น
	saved, err := s.repo.Save(ctx, order)
	if err != nil {
		return nil, err
	}

	// publish event แทนการ call payment-service โดยตรง
	// payment-service จะ subscribe และทำงานอิสระ
	event := OrderCreatedEvent{OrderID: saved.ID, UserID: req.UserID, Amount: req.Total}
	s.publisher.Publish(ctx, "order.created", event)

	return saved, nil
}
payment-service/handler.go 
// payment-service: subscribe event จาก order-service
// อิสระ deploy ได้เองโดยไม่ต้องรอ order-service
func (h *PaymentHandler) HandleOrderCreated(ctx context.Context, msg Message) error {
	var event OrderCreatedEvent
	json.Unmarshal(msg.Payload, &event)

	txID, err := h.gateway.Charge(ctx, event.UserID, event.Amount)
	if err != nil {
		// publish failed event กลับ — order-service จัดการเอง
		h.publisher.Publish(ctx, "payment.failed", PaymentFailedEvent{OrderID: event.OrderID})
		return nil
	}

	h.publisher.Publish(ctx, "payment.completed", PaymentCompletedEvent{
		OrderID: event.OrderID,
		TxID:    txID,
	})
	return nil
}

🧭 How to Choose?เลือกแบบไหนดี?

There is no universally best architecture — it depends on team size, domain clarity, and operational maturity ไม่มีสถาปัตยกรรมที่ดีที่สุดตลอดกาล — ขึ้นอยู่กับขนาดทีม, ความชัดเจนของ domain, และความพร้อมด้าน ops

🧱 Choose Monolith when:เลือก Monolith เมื่อ:
Startup / MVP / team < 5 people / still figuring out domain boundaries / speed matters most right now startup / MVP / ทีม < 5 คน / ยังไม่แน่ใจ domain boundary / ต้องการ ship เร็วที่สุด

Example: An e-commerce site just launching — start with monolith, refactor later when you understand the domain ตัวอย่าง: ร้านค้าออนไลน์ที่เพิ่งเปิดตัว — เริ่มด้วย monolith ก่อน แล้วค่อย refactor เมื่อเข้าใจ domain มากขึ้น
📦 Choose Modular Monolith when:เลือก Modular Monolith เมื่อ:
Team is growing (5–20 people) / need better code organization / not yet ready for ops overhead of microservices / want a clear migration path ทีมเติบโต (5–20 คน) / ต้องการจัดระเบียบ code ที่ดีขึ้น / ยังไม่พร้อมรับ ops overhead ของ microservices / ต้องการ migration path ที่ชัดเจน

Example: B2B SaaS with a team of 10–15 — clear module boundaries without the operational complexity ตัวอย่าง: SaaS B2B ที่มีทีม 10–15 คน — ขอบเขต module ชัดเจนโดยไม่เพิ่ม ops complexity
⚠️ Avoid Distributed Monolith — always:หลีกเลี่ยง Distributed Monolith เสมอ:
If you find that services must deploy together or call each other synchronously in chains, stop. Revert to a Monolith first, understand the domain boundaries clearly, then refactor toward proper Microservices. ถ้าพบว่า services ต้อง deploy พร้อมกัน หรือ call กันแบบ synchronous chain ให้หยุดทันที — revert กลับเป็น Monolith ก่อน เข้าใจ domain boundary ให้ชัดเจน แล้วค่อย refactor ไปเป็น Microservices ที่ถูกต้อง
🔬 Choose Microservices when:เลือก Microservices เมื่อ:
Very different scaling needs per service / large teams (Conway's Law) / clear domain boundaries / mature DevOps/K8s culture / independent release cadences per team แต่ละส่วนต้องการ scale ต่างกันมาก / ทีมใหญ่ (Conway's Law) / domain boundary ชัดเจนแล้ว / มีวัฒนธรรม DevOps/K8s ที่โตแล้ว / ทีมต้องการ release ได้อิสระ

Example: Fintech with separate payment team, analytics team, and risk team — each deploys independently on its own schedule ตัวอย่าง: Fintech ที่มีทีม payment แยกจากทีม analytics และทีม risk — แต่ละทีม deploy ได้อิสระตามรอบของตัวเอง
💡 Key Insight — Start Simpleหลักคิดสำคัญ — เริ่มต้นแบบง่าย
Most successful microservices architectures started as monoliths. Sam Newman (author of "Building Microservices") recommends: start with a monolith, understand your domain, then extract services when you have clear boundaries and a real scaling need. สถาปัตยกรรม microservices ที่สำเร็จส่วนใหญ่เริ่มต้นเป็น monolith ก่อน Sam Newman (ผู้เขียน "Building Microservices") แนะนำว่า: เริ่มด้วย monolith, ทำความเข้าใจ domain ของคุณ แล้วค่อย extract services เมื่อมีขอบเขตที่ชัดเจนและมีความต้องการ scale จริงๆ
